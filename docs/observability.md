# 연동 지표 및 모니터링 설계

설계만 하고 구현은 하지 않음

---

## 1. 모니터링이 답해야 하는 결정

- 지표는 사람이 그것을 보고 무언가를 결정할 때만 의미가 있다고 생각함
- 이 서비스에서 지표를 보고 내려야 할 결정은 셋이라고 판단함

| 결정 | 결정을 가르는 사실 |
|---|---|
| 지금 대응해야 하는가 | 고객이 받는 결과가 실제로 나빠졌는가 |
| 원인이 어디인가 | 공급사인가 아니면 이 서비스인가 |
| 설정값을 바꿔야 하는가 | 호출 상한 500ms, 동시 호출 상한 10, 검색 상한 2000ms, 커넥션 풀 100이 실제 상황과 맞는가 |

- 특히 이 설정값은 이 서비스에서 임의로 정한 부분이 있기 때문에 실제 데이터를 통해 모니터링 하면서 조절해야 함

---

## 2. 이 시스템에서 장애가 드러나는 방식

#### HTTP 상태로는 장애를 확인할 수 없음

- 검색은 공급사 하나가 죽어도 200에 부분 결과를 줌
- 에러율 그래프가 평평한데 고객은 절반의 숙소만 보고 있는 상태가 이 시스템에서는 장애가 아니라 설계된 동작임
- 따라서 응답에 성공했는지보다 응답의 결과가 얼마나 완전하게 채워졌는지를 먼저 봐야 함

#### 결과가 덜 온 원인은 두 쪽에서 나옴

- 공급사 쪽: 무응답, 공급사 오류, 스펙 위반 응답
- 이 서비스 쪽: 커넥션 풀 포화, 서킷 차단, 데드라인으로 인한 요청 중단
- 원인이 어느 쪽인지를 갈라야 공급사에 문의할지 이 서비스의 설정을 볼지 정할 수 있음

---

## 3. 측정 단위

- 측정 단위를 청크로 잡음
  - 검색 하나가 공급사당 여러 청크를 만들므로, 성공률을 검색 단위로 세느냐 청크 단위로 세느냐에 따라 같은 사건이 다른 숫자가 됨
- 청크가 어떻게 끝났는지를 여덟 가지로 나눔

```
요청한 청크
├─ 요청이 밖으로 나감
│   ├─ ok                결과 받음
│   ├─ timeout           호출 상한 초과
│   ├─ supplier_error    공급사가 실패 알림
│   ├─ malformed         해석 불가
│   └─ request_rejected  공급사가 요청 거부
├─ 요청이 밖으로 못 나감
│   ├─ circuit_open      서킷이 막음
│   └─ pool_exhausted    커넥션 풀 포화
└─ 잘림                  데드라인이 끊음
```

- 청크 하나는 위 여덟 중 정확히 하나로만 셈
- 이 분류는 어댑터가 응답을 해석한 뒤에야 정해짐
  - B는 HTTP 200 본문의 `resultCode`로 실패를 알리므로 상태 코드만으로는 `ok`와 `supplier_error`가 갈리지 않음

#### 데드라인에 잘린 청크를 따로 뺀 이유

- 두 종류가 섞여 있고 코드가 구분하지 못함
  - 이미 요청이 나갔으나 응답 전에 취소된 것
  - 동시 호출 상한에 걸려 아직 차례가 오지 않아 요청 자체가 나가지 않았던 것
- 그래서 나감과 못 나감 어느 쪽에도 넣지 않고 따로 셈

---

## 4. 무엇을 세고 재는가

#### 청크마다 세는 것

- 청크가 어느 분류로 끝났는지를 공급사별, 엔드포인트별로 셈

#### 나간 호출마다 재는 것

- 호출 하나의 소요 시간을 공급사별 및 엔드포인트별로 잼
- 데드라인에 취소된 청크는 요청이 나갔더라도 응답이 없어 잡히지 않음

#### 검색 한 건마다 세는 것

- 검색 결과가 온전한지, 일부만 왔는지, 실패했는지를 세고 걸린 시간을 잼
- 검색 한 건 안에서 결과를 받은 청크의 비율도 따로 봄
  - 청크를 전체로 묶은 값만 보면 트래픽이 많은 검색에 가려짐
  - 40청크 중 1개가 실패해도 청크 기준으로는 97.5%지만 그 고객은 결과를 온전히 받지 못했음
- 매핑 조회 구간을 따로 잼
  - 공급사와 무관한 이 서비스의 고정 비용임 
  - 동기 JDBC라 요청 스레드를 잡기 때문임
  - 이 값이 커지면 조회 구간에 대한 최적화가 필요함

#### 이 서비스의 자원 상태

- 공급사별로 커넥션 풀의 대기 건수와 서킷 상태를 봄
- 대기 건수가 0보다 크면, 공급사는 정상인데 커넥션을 기다리다 호출 상한을 넘겨 `timeout`으로 기록되는 실패가 시작됨
  - 이 경로는 예외만으로는 구분되지 않음
  - 대기 건수로만 알아챌 수 있음
- 풀 대기 건수와 서킷 상태는 아직 밖으로 내보내지 않음

#### 동기화 결과

- 공급사별 동기화 결과와 비활성화된 매핑 수를 셈
- 동기화는 하루 한 번이라 실패해도 즉시 보이지 않지만, 매핑이 낡으면 검색 결과가 조용히 나빠짐

---

## 5. 지표에 따른 원인 분석

- 위에서 만든 분류에 따르면 고객, 공급사, 우리 서비스 관점에서 문제가 생겼는지를 알 수 있음
- 요청이 밖으로 나간 청크와 요청한 청크를 보면 서비스가 호출을 내보냈는지에 대한 비율을 알게 됨
- 요청에 대한 결과를 받은 청크와 요청이 밖으로 나간 청크를 보면 우리 요청에 대해 공급사가 제대로 답을 했는지 알게 됨
- 요청에 대한 결과를 받은 청크와 요청한 청크를 보면 고객이 실제로 받은 결과의 비율을 알게 됨

| 신호 | 근거 |
|---|---|
| 서킷 OPEN 전이 | 최근 10건 중 실패 50%라는 판정이 이미 내려진 상태 |
| HALF_OPEN에서 다시 OPEN | 공급사 장애 지속 |
| 커넥션 풀 대기 건수 지속 상승 | 공급사가 정상인데 커넥션 대기로 타임아웃이 나기 시작하는 지점 |
| 비활성화된 매핑 수 급증 | 공급사가 목록을 일부만 준 경우 |
