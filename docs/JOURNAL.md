## Day 1 - 요구사항 분석 및 DB 설계 방향 결정

### 수행 내용
- 요구사항 문서를 정독한 뒤 두 공급사 스펙을 항목별로 비교하여 정리함
  - 요금 같은 경우 A는 날짜 별 세금 미포함 단가, B는 전제 날짜 기준 세금 포함 단가
  - 실패 같은 경우 A는 상태코드 B는 resultCode
- 요금 같은 경우는 공급처마다 왜 표시하는 방식이 다른가에 대한 의문이 생겨 조사함
- DB에 저장할 데이터를 생각한 뒤, 매핑 테이블 구조 설계

### 의사결정
- 숙소와 객실 타입은 1대 N 관계로 보이기 때문에 테이블을 숙소, 객실 타입으로 테이블을 분리함
- 별도의 식별자 컬럼을 둘 이유가 없다고 판단했기 때문에 숙소와 객실 타입의 PK를 내부 식별자로 사용함
- 다만 샤딩을 하게 된다면 auto increment pk에서 다른 발급 방식으로 바꿔야 하지만, 현재 규모에서는 이를 고려하여 만들 이유가 없다고 생각함
- 매핑테이블 동기화 과정에서 같은 데이터가 다른 PK로 저장될 가능성이 있으므로 유니크 제약조건을 걸음. 이 동기화는 upsert 로직으로 생각 중
- FK를 적용하지 않은 이유는 upsert 로직이기 때문에 불필요하기도 하고, 추후 리팩토링할 때에 비용이 큰 제약이 될 수도 있기 때문임
- 공급사가 모종의 이유로 기존에 공급하던 숙소를 공급하지 않을 수도 있다고 생각하여 last_synced_at 칼럼을 추가함 이를 통해 동기화 시점에 공급하지 않는 숙소를 보이지 않도록 처리하기 위함임
- 만약 실 서비스라고 생각한다면 created_at과 updated_at이 필요하다고 생각했음
  - created_at 같은 경우는 신규 입점 숙수를 추적하거나, 지난 달에 늘어난 공급사 A의 숙소 수와 같은 데이터를 다룰 때 필요하다고 생각함
  - updated_at은 실제 변경된 시각을 기록하기 때문에 고객이 특정 숙소가 안보인다고 문의하면 어느 시점부터 공급이 되지 않는다고 설명하는 경우에 필요하다고 생각함

### AI 활용
- 요금 표현 방식 차이에 대해 질문하여 업계 표준의 축이 날짜별 단가 / LOS 가격 이라는 것을 알게 됨
- 숙소와 객실 타입에 대한 DDL을 만들고 AI에게 검토를 요청했는데, 반정규화한 테이블을 제시하여, 이 부분을 최적화할 정도로 DB의 응답속도가 매우 빠르지 않아도 되고 오히려 이상현상이나 다른 부가적인 비용이 생긴다는 점 때문에 수용하지 않음
- pk를 내부식별자로 사용했을 때의 단점에 대해서 질문했더니 샤딩과 같은 경우에 정합성이 깨질 수도 있다고 하여 이를 참고함
- auto increment pk를 내부 식별자로 선택했을 때의 단점이 생각이 나지 않아서 AI를 사용하여 단점들을 확인함
- updated_at만 사용하게 되면 동기화 때 해당 로우가 업데이트 되지 않으면 이 값이 동기화 시점으로 변경되지 않는다는 AI의 조언을 받아 last_synced_at 칼럼을 추가함

## Day 2 - MOCK 구현, 숙소 리스트 동기화 설계 및 구현

### 수행 내용
- Mock Supplier 구현
- 숙소 리스트 동기화 설계
### 의사결정
- 동기화 과정을 추상화하여 전체 플로우를 먼저 생각함
  - 동기화 트리거 -> 동기화 서비스 -> 공급사 클라이언트 -> 공급사 API
  - 동기화 서비스는 공급사 클라이언트를 통해 데이터를 얻어 온 후 매핑 테이블에 upsert 로직을 수행함
  - 동기화 트리거는 스케줄링, 수동으로 실행, 서버 처음 시작 시 중 스케줄링과 수동 실행이 필요하다고 생각함
  - 서버 처음 시작 시 무조건 동기화하는 방식은 선택하지 않았음
    - 실제 서비스라면 배포, 재기동이 어느 정도 있을텐데, 그때마다 공급사 전체 목록을 호출하는 것은 낭비임
    - 다만 매핑 테이블이 빈 상태로 트래픽이 서버에 도달하게 되면 검색 결과가 빈 결과를 내놓을 수 밖에 없기 때문에, 매핑 테이블이 비어있는 경우에 처음 서버를 시작하는 경우에 한해서만 동기화를 실행하도록 함
- 멀티 인스턴스의 경우 동기화 과정을 분산하여 더 빠르게 처리할 수 있다고 생각함
  - 다만 멀티 인스턴스 상황에서 여러 인스턴스들이 다 같이 동기화 작업에 참여하는 작업이 정말로 필요한지에 대한 고민이 필요한데 이는 실제 데이터가 있어야 함 따라서 단일 인스턴스 기준으로 구현을 진행한 뒤 테스트를 통해 데이터를 얻어볼 생각임  
  - 동기화 과정은 하루 한 번 새벽시간대에 이루어진다고 가정함
  - 숙소리스트가 시간단위로 급변하는 것이 아니라고 생각했고, 만약 새로운 숙소가 숙소 리스트에 추가되었을 때 딜레이 되는 시간은 최대 하루라고 생각했음
  - 같은 이유로, 공급사 목록에서 제거된 숙소가 다음 동기화 전까지 검색에 노출될 수 있음. 이 구간 동안 해당 숙소는 재고 및 요금 조회에서 공급사가 응답하지 않아 결과에서 빠지거나 예약 불가로 보일 뿐이므로, 수용 가능하다고 생각함
  - 새벽시간대에 진행하는 것은 검색 서비스에 영향을 최소화 하기 위함임
  - 동기화 과정을 분산하여 실행하는 것은 단일 인스턴스로 동기화 과정을 실행해보았을 때, 모종의 이유로 새벽시간대에 마치지 못하는 경우에 도입해야 한다고 생각하여 테스트를 수행 후 분산처리를 고민하는 것이 옳다고 생각함 따라서 우선 단일 인스턴스를 기준으로 구현한 뒤 테스트를 통해 시간과 같은 품질을 측정해볼 것임
  - 그럼에도 불구하고 설계 과정이기 때문에 최악의 경우를 고려하여 생각해보기 위해 아래와 같은 생각을 함. 다만 실제 도입은 하지 않음.
    - 우선 간단하게 생각하기 위해 스케줄링만을 사용한다고 가정하여 생각을 진행함 
    - 멀티 인스턴스일 때 동기화에 관해 별다른 조치를 해놓지 않는다면 각 인스턴스마다 중복으로 공급사 API를 호출하게 되는데 현재 생각한 로직에서는 upsert 방식으로 매핑 테이블을 조작하기 때문에 DB의 정합성이 깨질 우려는 없지만, 낭비가 있다고 생각함
    - 위에서 언급한 낭비를 없애려면 하나의 인스턴스만 동기화를 실행하도록 하면 될텐데, 방법은 두 가지가 있다고 생각함
      - 리더를 선출하는 방식과, 동기화를 실행하는 시점마다 락을 잡은 인스턴스만 진행하는 방식
      - 리더 선출이 주는 이점은 정확히 하나의 실행 주체가 있다는 보장인데, 이 작업은 그 보장이 필요 없음
        - 두 개의 인스턴스가 잠깐 겹쳐 실행되어도 upsert로직과 유니크 제약 조건 덕분에 결과가 동일함
        - 반대로 모종의 이유로 실행 주체가 잠깐 없어서 한 회차를 건너 뛰어도, 하루 뒤 다음 회차에서 만회할 수 있음
    - 스케줄링이기 때문에 ShedLock, MySQL Named Lock, Redis 분산락을 생각해볼 수 있음
      - 위 분산락들은 공급사 단위로 인스턴스에게 동기화 과정을 분배할 수 있음
        - 다만 한 공급사가 압도적으로 많은 숙소를 주는 경우 이를 파티셔닝하는 것을 고려해야 함. 이 경우 공급사 목록 API가 한 번의 호출로 전체 데이터를 주는 현재 스펙과 달라지기 때문에 전제가 달라지는 별개의 설계로 보아 더 이상 생각을 진행하지 않음
      - 만약 위 3가지 락 중 하나를 도입한다면 그것은 ShedLock이 될것임
        - 기존 MySQL을 락 저장소로 쓰면서 어노테이션을 붙이면 구현이 거의 완료되므로 도입 비용이 가장 낮음
        - Redis의 락 기능 자체로 충분하지만, 별도의 인프라가 필요하여 부적합함
        - MySQL Named Lock은 락에 만료 장치가 없어, 멈춘 프로세스나 커넥션 풀 반납으로 락이 잔존하는 경우를 코드로 직접 관리해야 하는 부담이 있음 
- 공급사 클라이언트가 새로 생길 때마다 코드가 추가는 불가피하므로, 목표를 추가가 기존 코드 수정으로 번지지 않게 격리하는 것으로 정했음
  - 새로 들어온 개발자가 온보딩 기간에 만약 이 코드를 익힌다고 생각했을 때 수정할 포인트가 많다면 온보딩에 들어가는 비용이 커짐
  - 신규 공급사 추가가 기존 파일을 건드리면 휴먼에러와 같이 모종의 이유로 기존에 문제 없이 동작하던 기존 공급사 연동에 버그가 생길 수도 있음
  - 따라서 공급사별로 응답을 달리 처리하는 로직을 SupplierClient 인터페이스의 구현체에 넣음으로써 책임을 위임함
  - 새로운 공급사 추가는 새 구현체 클래스를 추가하면 컴포넌트 스캔에 의해 List<SupplierClient>로 주입되므로 기존 코드를 수정하지 않음으로써 확장에는 열려있고 수정에는 닫혀있는 구조를 만듦

### AI 활용
- Mock Supplier 구현하고 실제 동작에 대해 간단히 실행해보라고 했을 때 sleep 메서드 호출 시 interrupt로 원래 흐름으로 조기 복귀해도 흐름이 이어져 무응답이어야 할 요청이 성공 응답으로 끝날 수 있다는 경우를 알게 되어 sleep 중 중간에 일어났는지 구분하는 코드를 넣도록 함
- 멀티 인스턴스 환경에서 하나의 공급사가 방대한 양의 숙소 데이터를 제공해야 하는 경우 처리 방법이 떠오르지 않아서 AI에게 질의했더니 batch를 사용하는게 적합하다는 응답이 돌아왔지만 spring batch를 사용해본 적이 없기 때문에 이해하기 위해 플로우를 추상화하여 설명하게끔 AI에게 요구함
  - 이 방법이 맞다고 주장하길래 트랜잭션 관련해서 데이터의 정합성이 훼손될 여지가 있는지 질문했더니 있다고 하여 정합성이 깨지는 시나리오를 만들어보라고 한 뒤 논리적으로 타당한지 검토함
  - 따라서 만약에 이 방법을 적용하려면 추가적인 안전장치가 필요하기 때문에 개발 비용이 매우 크다고 생각함
- 멀티 인스턴스 환경에서 리더를 선출하는 방법이 zookeeper와 같은 코디네이터 뿐이라고 제시하길래 분산락을 통해 리더를 선출하는 것이랑 어떤 차이가 있는지 설명하도록 했고, 이 시스템에서 매핑 테이블을 업데이트하는 로직에는 upsert를 사용하므로 리더를 선출하는 의미가 없기 때문에 만약 리더가 필요하다면 분산락을 잡는 것이 그나마 낫다고 생각하게 됨
- 구현할 때 생각한 클래스 다이어그램이랑 일치하는지 확인하기 위해 생각한 구조를 AI에게 입력하여 검토를 요청함
- SupplierAClient를 구현하고 서버를 시작했는데, DB 스키마가 생성되지 않는 점을 발견하여 AI에게 원인을 분석하도록 요청함
  - SpringBoot 4 이상에서는 flyway를 사용할 때 추가적인 의존성이 필요한 점을 AI에게 답변 받아 이를 받아들여 수정함
- 어댑터 세부 구현 계획을 세울 때 예외 클래스들을 어떻게 구성할지에 대한 의논을 함
  - 예외 부모를 sealed로 선언하면 하위 타입들이 컴파일 타임에 검증이 되어 예외를 분기하여 사용하는 곳에서 유형 누락이 발생하면 컴파일 시점에 알 수 있다는 점을 알게 되어 이를 적용함
  - 새 공급사가 기존 분류에 없는 실패를 들고 오면 기존 예외 코드를 수정해야 한다는 점이 있어서 이는 OCP 위반인 것 같아 잘못된 설계가 아닌지 AI에게 되물었는데, 실패를 분류하는 것은 공급사가 아니라 이 도메인의 개념이라 어떤 설계로도 격리할 수 없다는 답을 검토함.
  - 단점으로는 확장하는 경우 수정이 사용하는 곳에서 switch 문의 수정이 강제되고, 테스트에서 sealed 예외 부모의 임의 하위 타입을 만들 수 없지만 이는 수용 가능한 수준이라고 판단함

## Day 3 - 동기화 검증 및 타임존 통일

- 확인 과정에서 시각 컬럼의 타임존이 섞여 있는 것을 발견하여 UTC로 통일함

### 의사결정
- 같은 행의 두 시각 컬럼이 서로 다른 기준으로 기록되고 있었음
  - `created_at`/`updated_at`은 DB의 `CURRENT_TIMESTAMP(6)`가 찍고, `last_synced_at`은 애플리케이션이 `LocalDateTime.now()`로 찍음
- 저장은 UTC로 하고 표시 시점에 변환하는 방식을 택함
  - 서버의 로컬 시간대에 저장을 맡기면 배포되는 곳이 바뀔 때 같은 컬럼에 다른 기준의 값이 섞일 수도 있음

### AI 활용
- 동기화 시나리오 검증을 AI에게 실행시키고 결과를 받았는데, 그 과정에서 `created_at`과 `last_synced_at`이 정확히 9시간 어긋나 있다는 지적을 받음
  - 값을 직접 확인하여 사실인 것을 확인했고, 이를 고침
