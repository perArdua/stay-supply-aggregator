## 통합 검색 흐름 설계

#### 엔드포인트
```
GET /api/v1/stays/search?checkIn=2026-09-01&checkOut=2026-09-04&adults=2&children=0
```

| 파라미터 | 타입 | 설명 |
|---|---|---|
| `checkIn` | date | 체크인일 |
| `checkOut` | date | 체크아웃일이며 숙박일에 포함되지 않음 |
| `adults` | int | 성인 인원 |
| `children` | int | 아동 인원 |

- 검색 조건은 날짜와 인원이며, 조회 대상은 보유한 숙소 전체임
- 요청 검증은 조회 조건 객체(`AvailabilityQuery`)를 만드는 시점에 함
  - `checkIn`과 `checkOut`이 있어야 함
  - `checkOut`이 `checkIn`보다 뒤여야 함
  - `adults`가 1 이상, `children`이 0 이상이어야 함
- 컨트롤러가 아니라 객체 생성 시점에 둔 이유
  - 잘못된 조건을 담은 객체 자체가 만들어지지 않게 함
  - 어댑터가 따로 방어할 필요가 없어짐
  - 검색 외의 경로에서 이 객체를 만들어도 같은 검증이 걸림
- 위반 시 컨트롤러가 400으로 변환함

#### 흐름
```
검색 요청
  → 매핑 로드
  → 공급사별로 코드를 묶고 50개 단위로 분할
  → 공급사 병렬, 청크 병렬로 호출
  → 각 응답을 SupplierOffer로 정규화
  → 매핑을 붙여 StayOffer로 변환
  → 병합해 응답
```

---

### 모델을 두 단계로 둠
- 공급사 응답에는 공급사 코드가 담겨 있고, 고객에게 줄 응답에는 내부 식별자가 담겨야 함
- 이 변환을 하려면 매핑 테이블을 조회해야 함. 즉 변환 지점은 DB를 아는 곳이어야 함
- 공급사를 호출하는 계층은 DB를 모르고 만약 공급사를 호출하는 계층에서 변환하면 그 계층이 DB에 의존하게 됨
- 그래서 모델을 둘로 두고 변환을 호출 계층 바깥에서 함

| 모델 | 만드는 곳 | 식별자 |
|---|---|---|
| `SupplierOffer` | 공급사 호출 계층 | 공급사 코드 |
| `StayOffer` | `SearchService` | 내부 식별자 |

- `SearchService`는 조회할 코드를 꺼내기 위해 매핑을 읽으므로 그 결과를 변환에 그대로 씀
- 잃는 것은 같은 상품을 나타내는 모델이 둘이 되어 필드가 상당 부분 겹친다는 점임
  - 만약 수정이 필요한 상황이 생긴다면, 한쪽만 고치고 다른 쪽을 빠뜨릴 수 있음
  - 그럼에도 불구하고 호출 계층의 경계를 지키는 편이 낫다고 판단함

#### StayOffer에는 supplier 필드를 둠
- 동기화쪽에서 `PropertyListing`에는 supplier를 두지 않았지만 여기에서는 여러 공급사의 결과를 한 리스트에 병합하므로 반환한 객체가 스스로 출처를 나타내지 못하기 때문에 공급사를 표시하는 필드를 둠

### 요금 표준

#### 기간 전체 총액을 표준으로 삼음
- A는 날짜별 세금 별도 단가를 주고 B는 기간 전체 세금 포함 총액을 주므로 하나로 통일해야 함
- 숙박 하는 날에 따라서 단가가 달라진다는 점을 생각해보았을 때 B가 주는 기간 전체 가격이 1박 가격들의 합이 아닐 가능성이 높다고 생각함
- 따라서 총액을 표준으로 삼음
  - A의 총액은 각 날짜의 `nightlyRate`와 `taxAmount`를 더해 합산한 값임
  - B의 총액은 `totalPrice`를 그대로 씀
- 사용하는 사람입장에서도 생각해보았는데, 어떤 기간동안 어디에 머물지를 결정할 때 1박 가격들을 확인하고 예약을 하는 것이 아니라 최종 결제할 금액을 기준으로 생각한다고 판단함

##### 얻는 것
- 두 공급사의 상품을 같은 기준으로 비교할 수 있음
- 어느 공급사에서 왔는지와 무관하게 응답 형태가 같음

##### 잃는 것
- 세금 표현이 공급사마다 달라짐. A는 세액을 알 수 있고 B는 알 수 없어 `taxAmount`가 한쪽만 채워짐
  - 세액이 얼마인지 표시해야 하는 요구사항이 생기면 수정이 필요함 
- 부분 취소나 일부 날짜 변경이 생기면 합리적인 환불액을 산정할 근거가 없음
  - A는 날짜별 값을 갖고 있었으나 버렸고 B는 애초에 없음

##### 생각해봤지만 설계에 반영하지 않은 것들
- 날짜별 단가를 표준으로 삼고 B의 총액을 박수로 나눔
  - 공급사가 주지 않은 값을 만들어내기 때문에 고객에게 보여주는 숫자가 사실이 아님
- 두 형태를 모두 표준에 담고 공급사에 따라 한쪽만 채움
  - 공급사 간 차이가 응답 표면에 그대로 드러남
  - 클라이언트가 어느 필드를 볼지 공급사별로 분기해야 하므로 이 코드의 책임을 다른 개발자에게 넘기는 행위가 됨

#### 필드 구성
| 필드 | 의미 | A | B |
|---|---|---|---|
| `totalAmountIncludingTax` | 기간 전체 고객 결제 금액 | 요청 기간 날짜의 합산. 날짜가 빠지면 `null` | `totalPrice` |
| `taxAmount` | 그중 세금 | 요청 기간 날짜의 `taxAmount` 합산. 날짜가 빠지면 `null` | `null` |
| `currency` | 통화 | 응답 그대로 | 응답 그대로 |
| `breakfastIncluded` | 요금에 조식이 포함되는지 | 응답 그대로 | 응답 그대로 |

- 이름에 `IncludingTax`를 넣은 이유
  - `totalAmount`만으로는 세금 포함 여부가 드러나지 않기 때문에 명확히 하기 위해 넣음
  - net과 gross는 공급사 스펙의 용어이므로 자사 모델에 쓰지 않음
- `taxAmount`를 B에서 `null`로 두는 이유
  - B는 `totalPrice`에 세금이 포함되어 있다는 것만 알려주고 세액은 주지 않음
  - 만약 null이 아닌 0으로 값을 놓는다면, 세금이 없는 상품과 구분되지 않음
- `breakfastIncluded`를 함께 노출하는 이유
  - 예시 데이터에서 같은 객실을 A는 조식 없이 429,000원에, B는 조식을 포함해 452,000원에 팜
  - 이 필드가 없으면 고객이 금액만 보고 조건이 다른 상품을 비교하게 됨
  - 요금을 비교 가능한 형태로 내놓는 것이 통합의 목적이므로 조건을 함께 노출함

#### 합산 대상을 요청 기간의 날짜로 한정함
- A의 응답에서 요청 기간(checkIn 이상 checkOut 미만)에 해당하는 날짜만 골라 더함
- A가 기간 밖 날짜를 얹어 보내도 총액에 넣지 않음
  - 예약 가능 객실 수는 요청 기간만 보는데 요금이 응답 전체를 더하면, 같은 상품의 재고와 금액이 서로 다른 기간을 가리키게 됨

#### 요청 기간의 날짜가 빠져 있으면 총액과 세액을 함께 null로 둠
- 4박을 요청했는데 A가 사흘치 요금만 주는 경우임
- 그대로 합산하면 3박 금액이 4박 상품의 가격으로 고객에게 보임
- 재고는 모르는 날을 0으로 보아 틀려도 안전한 쪽으로 틀리지만, 금액에는 그런 방향이 없어 그냥 틀린 값이 됨
- 총액을 믿을 수 없는데 세액만 내보내는 것은 앞뒤가 맞지 않아 둘을 함께 비움
  - B의 `taxAmount`를 0이 아니라 `null`로 둔 것과 같은 규칙임
- 같은 상황에서 B의 상품은 `totalPrice`가 그대로 나감
  - A는 날짜마다 요금이 붙어 오므로(`ADailyRate`에 date와 nightlyRate가 함께 있음) 요청한 박수와 받은 날짜 수를 비교해 누락을 알 수 있음
  - B의 요금은 `totalPrice` 하나뿐이고 날짜가 붙어 있지 않음. 그 금액이 며칠치인지 B가 알려주지 않으므로 이 서비스가 누락을 판정할 근거가 없음
  - B도 날짜별 잔여 객실 수는 주므로 재고 쪽 누락은 알 수 있고 그때 `availableRooms`는 0이 됨. 다만 잔여 객실 수가 빠진 날이 있다고 해서 요금도 그만큼 모자라다는 뜻은 아니므로 요금 판정의 근거로 쓸 수 없음
- 그래서 날짜가 빠진 같은 상황에서 A는 요금이 `null`이고 B는 값이 그대로 나가는 차이가 생김
  - B가 금액에 기간을 붙여 주지 않는 한 이 서비스가 판정할 수 없으므로 지금은 그대로 둠

### 예약 가능 객실 수

#### 연박 판정은 최솟값으로 함
- 예약 가능 객실 수의 정의가 요청 기간 전체를 예약할 수 있는 객실 수임
- 3박 중 하루라도 재고가 0이면 그 기간 전체를 예약할 수 없음
- 따라서 기간 내 날짜별 `remainingRooms`의 최솟값을 취함

```
A-10023  재고 3, 1, 5  →  최솟값 1
A-10044  재고 2, 0, 4  →  최솟값 0
```

#### 날짜가 일부 누락된 응답은 0으로 봄
- 3박을 요청했는데 응답에 2일치만 오는 경우가 있을 수 있음
- 누락된 날의 재고를 모르는 상태이며, 이를 있다고 가정하면 예약할 수 없는 상품을 판매 가능으로 노출하게 됨
- 그래서 그 상품은 예약 불가 상태로 놓는 것이 맞다고 생각함
- 검토했지만 적용하지 않는 부분
  - 응답에 없는 날짜를 무시하고 응답으로 온 날짜끼리만 최솟값을 구하는 방법
    - 3박을 요청했는데 2일치만 오면, 그 2일치만 보고 예약 가능하다고 판단하게 됨
    - 빠진 하루에 방이 없어서 예약이 실패해도 검색 결과에는 예약 가능으로 나옴
  - 스펙 위반으로 보고 예외를 던지면 하나의 이상 현상이 그 공급사 결과 전체를 날림

#### 예약 불가 상품도 응답에 포함함
- `availableRooms`를 0으로 두어 그대로 노출함
- 고객이 그 숙소의 존재를 알고 날짜를 바꿔 다시 검색할 수 있음
- 응답에서 빼면 없는 숙소와 그 날짜에 방이 없는 숙소가 구분되지 않음
- 다만, 단점으로는 응답 크기가 커지고 클라이언트가 0을 걸러내는 처리를 해야 한다는 점이 있음
  - 응답 크기가 커지는 문제는 키워드, 페이징 등을 사용하면 해결가능 하지만, 문서에서 다루는 범위 밖임
- 예약 가능 여부를 나타내는 별도 boolean 필드는 두지 않음
  - `availableRooms`가 0인 것이 곧 예약 불가이므로 같은 사실을 두 필드로 표현하게 됨

### 병렬 호출과 응답 시간
#### 공급사 간 병렬
- 공급사별 호출을 동시에 시작하고 모두 도착하면 결과를 합침
- 각 호출은 실패해도 예외를 밖으로 내보내지 않고 실패했다는 값을 내보내게 함
  - 그렇게 하지 않으면 한 공급사의 실패가 전체를 실패로 만들어, 성공한 공급사의 결과까지 버려짐

#### 청크 분할
- 재고 요금 조회는 한 번에 최대 50개 숙소 코드를 받으므로 코드 목록을 50개 단위로 나눔
- 예를 들어서 A는 120개를 준다면 (50, 50, 20)으로 청크 3개로 나눔, B는 80개를 준다면 (50, 30)인 청크 2개로 나눔
  - 총 5회 호출임

- 청크도 동시에 호출함
  - 순차로 하면 응답 시간이 숙소 수에 비례해 늘어나 숙소가 수천 개면 검색이 성립하지 않음
- 다만 동시에 나가는 호출 수에 상한을 둠
  - 고객 요청 한 건이 청크 수와 공급사 수를 곱한 만큼의 외부 호출로 늘어남
  - 고객 한 명이 호출을 너무 많이 차지하는 것은 다른 고객에게 피해가 되기 때문임
- 상한은 전역 하나가 아니라 공급사별로 둠
  - 호출 한도는 공급사가 각자 거는 것이므로 그 단위로 두는 것이 맞다고 생각함
  - 따라서 전역적인 상한은 공급사 수 × 상한이 됨
- 공급사 하나당 동시에 10개까지만 나가게 함
  - 요청 한 건 기준으로 공급사 2곳이면 최대 20개가 동시에 나감
  - 커넥션 풀이 감당하지 못하면 초과분이 풀에서 대기하고, 그 대기 시간이
    호출 하나의 시간 상한을 갉아먹음
  - 그러면 공급사는 멀쩡한데 `TIMEOUT`으로 응답을 보는 가짜 실패가 생김
  - 이 문제는 실제로 발생하는 것을 확인하고, 대기 큐까지 꽉 차 호출이 거부되는 쪽은 `POOL_EXHAUSTED`로 에러 처리함
- 이 계산의 한계
  - 검색이 한 건이라고 간단한 가정을 두고 진행함
  - 추후 여러 상황을 고려하여 반영할 계획임

#### 병렬 실행하지만 전체 응답 시간에 상한을 둬야함
- 완료 조건을 모든 호출이 끝나는 시점이 아니라 정해진 시간이 되는 시점으로 둠
  - 모두 기다리면 응답 시간이 가장 느린 호출에 묶이며 청크 수가 늘수록 상한이 사라짐
  - 데드라인을 두면 청크 수와 무관하게 응답 시간의 상한이 고정됨
- 이로 인해 동시 호출 수를 정하기 쉬워진다고 생각함
  - 시간에 상한이 없으면 동시 호출 수가 곧 응답 시간을 결정하는 지배적인 변수임 
  - 시간에 상한이 있으면 응답 시간은 상한이 지키게 되므로 동시 호출 수는 커넥션 풀이 감당할 수 있는 범위를 고려하여 정하면 됨
- 다만, 이 방법은 시간 안에 호출이 끝나지 않은 청크가 생길 수 있으며 이로인해 부분 실패가 생기게 됨
  - 응답이 느려지는 대신 결과가 덜 완전해지는 쪽을 선택한 것인데, 고객입장에서는 생각해보았을 때 응답이 느린 것이 더 안좋다고 생각하기 때문임

#### 고려했었던 방법들
- 일정 수의 응답이 오면 마감하는 방식
  - 응답 하나가 빠지면 그 청크의 숙소가 통째로 사라지며, 어느 숙소가 빠질지 통제할 수 없음
  - 데이터 흐름에 대해서는 코드를 작성한 개발자가 어느정도 책임을 져야하는데, 통제 불가능한 플로우가 존재한다는 것 자체가 잘못됐다고 생각함
- 검색 경로에서 공급사를 호출하지 않고 캐시에서 읽는 구조
  - 짧은 TTL을 갖는 캐시를 두고 검색 경로가 공급사 응답을 기다리지 않게 하는 방법이 있음 
  - 도입한다면 캐시 정합성의 허용 오차와 스탬피드 방지가 함께 필요함
  - 설계를 고민하는 시간이 더 중요하다고 생각하여 시간이 남는다면 할 것임

### 부분 실패 처리

#### 응답 형태
| 상황 | HTTP | 본문                          |
|---|---|-------------------------------|
| 전체 성공 | 200 | `offers`와 `suppliers`        |
| 일부 공급사 실패 | 200 | 성공한 `offers`와 `suppliers` |
| 모든 공급사 실패 | 503 | `code`, `message`와 `suppliers` |

- 부분 실패를 200으로 두는 이유
  - 고객에게 보여줄 결과가 실제로 있으므로 요청 처리가 실패한 것이 아님
  - 어느 공급사가 왜 실패했는지는 상태 코드로 표현할 수 없고 본문을 봐야 함
- 전체 실패를 503으로 두는 이유
  - 고객에게 보여줄 결과가 하나도 없음
  - 200으로 두면 그 날짜에 방이 없는 경우와 공급사가 전부 죽은 경우가 같은 상태가 됨
  - 모니터링에서 전면 장애가 성공으로 집계되어 알람이 걸리지 않음
- 잃는 것
  - 클라이언트가 두 가지 본문 형태를 다뤄야 함
  - 5xx이므로 클라이언트의 재시도가 발동할 수 있으며, 공급사가 죽은 상황에서 재시도가 몰림
    - `Retry-After` 헤더로 재시도를 몰리는 것을 방지할 수도 있으므로 추후 설계에서 반영할 예정임

#### 공급사 상태
| 상태 | 의미 |
|---|---|
| `OK` | 요청한 모든 청크가 성공함 |
| `PARTIAL` | 일부 청크만 성공했으며 성공한 청크의 결과는 응답에 포함됨 |
| `TIMEOUT` | 응답이 시간 안에 오지 않음 |
| `SUPPLIER_ERROR` | 공급사가 실패를 알림 |
| `REQUEST_REJECTED` | 공급사는 정상인데 우리 요청을 거부함 |
| `MALFORMED_RESPONSE` | 응답은 왔으나 해석할 수 없음 |
| `CIRCUIT_OPEN` | 서킷이 열려 호출하지 않음 |
| `POOL_EXHAUSTED` | 커넥션 풀이 포화되어 호출하지 못함 |

- 청크 일부가 실패해도 성공한 청크의 결과는 버리지 않음
  - 공급사 하나가 실패해도 나머지로 응답한다는 원칙을 청크 단위에도 적용함
- 잃는 것
  - `PARTIAL`일 때 고객은 일부 숙소가 빠진 결과를 보지만 무엇이 빠졌는지는 알 수 없음
  - 응답은 정상으로 보이므로 결과가 불완전하다는 사실이 고객에게 드러나지 않음

#### 청크마다 실패 이유가 다를 때 무엇을 대표로 삼는가
- 한 공급사의 청크가 서로 다른 이유로 실패할 수 있으므로 공급사 상태 하나로 줄일 기준이 필요함
- 하나라도 성공한 청크가 있으면 이유와 무관하게 `PARTIAL`임. 성공한 결과가 응답에 들어 있다는 사실이 먼저이기 때문임
- 전부 실패했을 때는 아래 순서에서 앞선 것을 공급사 상태로 올림

| 순서 | 상태 | 앞에 둔 이유 |
|---|---|---|
| 1 | `POOL_EXHAUSTED` | 이 서비스의 자원 부족이라 다른 실패들의 원인일 수 있음. 먼저 보여야 엉뚱한 곳을 보지 않음 |
| 2 | `REQUEST_REJECTED` | 공급사는 정상인데 우리 요청이 거부됨. 우리가 고칠 수 있는 문제임 |
| 3 | `MALFORMED_RESPONSE` | 응답은 왔으므로 공급사는 살아 있음. 해석 규칙 문제임 |
| 4 | `TIMEOUT` | 공급사가 느림 |
| 5 | `SUPPLIER_ERROR` | 공급사가 실패를 알림 |
| 6 | `CIRCUIT_OPEN` | 호출 자체를 하지 않았으므로 이번 시점의 정보가 가장 적음 |

- 우리 쪽에서 고칠 수 있는 것을 앞에, 공급사 쪽 사정을 뒤에 둠
- 데드라인에 잘려 도착하지 못한 청크는 `TIMEOUT`으로 셈. 원인은 어댑터 타임아웃과 다르지만 고객에게 드러나는 결과가 같기 때문임

#### 재시도 기준
| 상태 | 재시도가 의미 있는가 | 고칠 곳                                         |
|---|---|-------------------------------------------------|
| `TIMEOUT` | 있음 | 공급사 또는 우리 타임아웃 설정                  |
| `SUPPLIER_ERROR` | 있음 | 공급사측 서버 오류                              |
| `REQUEST_REJECTED` | 없음 | API 키, 파라미터, 호출 한도 등에 따른 요청 거절 |
| `MALFORMED_RESPONSE` | 없음 | 받는 데이터가 예상과 다름                       |
| `CIRCUIT_OPEN` | 없음 | 서킷이 닫힐 때까지 기다려야 함                  |
| `POOL_EXHAUSTED` | 없음 | 우리 쪽 자원 부족이라 즉시 재시도하면 포화를 키움 |

- 재시도는 재시도의 의미가 있는 곳에서 사용해야 한다고 생각함
- 공급사 서버가 다운 됐는데 계속 요청하는 것은 의미가 없음
- 이에따라 위의 표처럼 기준을 나눔

### 매핑 테이블에 없는 응답 처리
- 공급사 응답에 온 숙소 코드와 객실 타입 코드가 매핑에 없으면 그 항목을 제외함
- 내부 식별자를 만들 수 없어 응답에 담을 수 없기 때문임
- 동기화 이후 공급사가 객실 타입을 추가한 경우에 발생함
- 잃는 것은 다음 동기화까지 최대 하루 동안 그 상품이 노출되지 않는다는 점임
- 로그는 요청당 한 줄로 묶어 WARN으로 남김
- 응답에는 표시하지 않음
  - `suppliers`의 상태는 공급사 조회의 성공 및 실패를 표현하는 자리임
- 고려했었던 방법들
  - 검색 중에 매핑을 발급하는 방식을 잠깐 생각했었으나 검색 경로에 DB 쓰기가 들어와서 책임이 섞임
  - 매핑되지 않은 것을 발견했을 때 동기화를 비동기로 거는 방식은 노출 지연을 몇 분으로 줄일 수 있으나, 검색마다 트리거가 걸리지 않도록 별도의 조치가 필요함
---

### 같은 숙소를 파는 두 공급사의 상품을 하나로 합치지 않음
#### 공급사가 많아지면 합칠 필요가 있음
- 이를테면 유명 호텔 하나를 공급사 수십 곳이 제공하게 되면 그 숙소가 목록을 채우게 됨
- 고객은 같은 호텔을 넘기기 위해 페이지를 넘기거나 스크롤 다운을 해야함
- 즉 이 경우 검색 기능이 제대로 동작하지 않는 상황이라고 봐도 됨

#### 그럼에도 불구하고 지금 합치지 않는 이유
- 공급사들이 같은 숙소를 판다는 사실을 조건문으로 알아내기 어려움
- 이로인해 사람이 직접 관여해야 하고 공급사에 변경이 생기면 검증이 필요함
- 또한 같은 숙소로 판정되어 이를 고객이 예약했는데, 실제로 잡힌 숙소가 다를 수도 있다는 위험이 있음
- 즉, 이러한 검증 시스템은 별도의 시스템이나 모듈이 필요하다고 생각됨
