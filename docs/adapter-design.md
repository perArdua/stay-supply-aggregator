## 공급사 어댑터 설계

### 제약사항
- 동기화 등 도메인 계층이 의존하는 것은 공통 인터페이스(`SupplierClient`)와 자사 표준 모델(`PropertyListing`, `RoomTypeListing`)임
  - 요구사항상 공급사별 형식이 도메인 계층으로 새어 나가지 않게 경계를 두어야 함
- 공급사 전용 DTO는 해당 어댑터 클래스 내부 record로 두어 패키지 밖으로 나가면 안 됨
- 공급사 API의 실패 표현도 데이터와 마찬가지로 공급사별로 다름. 이 차이를 어댑터가 공통 예외로 변환하므로, 호출하는 쪽은 공급사별 실패 방식의 차이를 알지 못함

---

### 표준 모델에 출처 공급사를 표시할 것인가

#### 배경
- 동기화는 여러 공급사의 숙소 목록을 받아 매핑으로 저장함
- 표준 모델이 자기가 어느 공급사에서 왔는지를 들고 다닐지 정해야 함

#### 검토한 선택지

| 선택지 | 얻는 것 | 잃는 것 | 판단 |
|---|---|---|---|
| (a) 모델에 `supplier` 필드를 둠 | 인스턴스만 보고 출처를 알 수 있음 | 각 클라이언트가 자기 supplier를 매번 채워 넣어야 하고, 잘못 채워도 컴파일러가 잡지 못함 | 미채택 |
| (b) 반환한 클라이언트를 출처로 봄 | 채워 넣을 값이 없어 잘못 채울 여지 자체가 없음 | 여러 공급사의 결과를 한 리스트에 섞는 순간 출처가 사라짐 | **채택** |

#### 채택 이유
- 반환한 클라이언트가 이미 출처이므로 모델이 자기 출처를 또 들고 다닐 필요가 없음
- 동기화는 공급사 단위로 순차 처리하며 결과가 섞이지 않으므로 이 구조가 성립함

#### 트레이드오프
- 이것은 모든 모델에 적용되는 원칙이 아니라, 결과가 섞이지 않는다는 전제 위의 선택임
- 결과를 섞어 다루는 지점이 생기면 그 지점의 모델에는 출처를 명시해야 함
  - 검색이 그런 경우임. 여러 공급사의 결과를 한 리스트로 병합하므로 반환한 객체가 스스로 출처를 나타내지 못하기 때문에, 검색의 `StayOffer`에는 supplier 필드를 둠

### 공급사별 실패 표현을 통일할 것인가

#### 배경
- 공급사마다 실패를 표현하는 방식이 다름. A는 HTTP 상태로 알리고 B는 200 본문의 `resultCode`로 알림
- 이 차이를 어디까지 어댑터가 흡수할지 정해야 함

#### 검토한 선택지

| 선택지 | 얻는 것 | 잃는 것 | 판단 |
|---|---|---|---|
| (a) 공급사의 실패 표현을 그대로 올림 | 공급사가 준 정보를 잃지 않음 | 호출부가 A는 HTTP 상태, B는 `resultCode`를 알아야 하고 신규 공급사마다 호출부에 판정 코드가 늘어남 | 미채택 |
| (b) 어댑터가 공통 예외로 변환 | 호출부가 공급사별 실패 표현을 몰라도 됨 | 공급사 고유의 실패 정보가 분류로 뭉개짐 | **채택** |

#### 채택 이유
- 실패를 표현하는 방식은 다르지만 실패의 의미를 추상화하면 같음
- (a)는 신규 공급사가 추가될 때마다 호출부에 해당 판정 코드를 넣어야 하며, 이는 격리의 목적과 반대임

#### 통일 결과
- 공급사가 응답한 실패를 타임아웃 / 공급사 측 오류 / 요청 측 오류 / 스펙 위반 응답의 네 분류로 나누고 각각을 별도 예외 클래스로 둠
- 여기에 응답 자체가 없는 두 경우를 더해 예외 계열은 모두 여섯 개임

| 의미 | Supplier A | Supplier B | 통일 결과 |
|---|---|---|---|
| 타임아웃 | connect/엔드포인트별 상한 초과 | 동일 | `SupplierTimeoutException` |
| 공급사 내부 오류 | HTTP 500 | 200 + `E500` | `SupplierServerException` |
| 일시적 장애 | HTTP 503 | 200 + `E503` | `SupplierServerException` |
| 잘못된 요청 | HTTP 400 | 200 + `E400` | `SupplierClientErrorException` |
| 인증 실패 | HTTP 401 | 200 + `E401` | `SupplierClientErrorException` |
| 호출 한도 초과 | HTTP 429 | 200 + `E429` | `SupplierClientErrorException` |
| 미지의 resultCode | — | 200 + 미정의 코드 | `SupplierMalformedException` |
| 성공 선언 + 본문 없음 | 빈 리스트로 처리 | `SupplierMalformedException` | 공급사별로 다름 |
| 역직렬화 실패 | 발생 시 | 발생 시 | `SupplierMalformedException` |

- 이후 요청이 공급사에 나가지 못하는 경우 두 가지가 계열에 더해짐
  - 서킷이 열려 호출하지 않은 `SupplierCircuitOpenException`
  - 커넥션 풀이 포화되어 호출하지 못한 `SupplierPoolExhaustedException`
  - 위 표는 공급사의 응답을 분류한 것인데 이 둘은 응답 자체가 없으므로 넣지 않음

### 분류를 얼마나 잘게 나눌 것인가

#### 배경
- 통일하기로 정한 뒤, 공급사의 실패 코드를 몇 개의 분류로 접을지 정해야 함
- A의 401과 429는 실제 대응이 다름. 401은 인증 문제라 사람이 고쳐야 하고, 429는 기다리면 풀림

#### 검토한 선택지

| 선택지 | 얻는 것 | 잃는 것 | 판단 |
|---|---|---|---|
| (a) 공급사의 실패 코드를 1:1로 예외에 대응 | 401과 429처럼 대응이 다른 실패를 구분할 수 있음 | 아무도 쓰지 않는 분기가 생기고 공급사가 늘 때마다 계층이 벌어짐 | 보류 |
| (b) 소비처가 구분할 수 있는 만큼만 나눔  | 계층이 작게 유지되고 분기가 전부 실제로 쓰임 | 401과 429가 같은 `SupplierClientErrorException`이 됨 | **채택** |

- (a)를 미채택이 아니라 보류로 둔 이유는 지금 틀린 방식이어서가 아니라 아직 소비처가 없기 때문임. 만약 재시도 정책을 도입하면 a를 고려해야 함

#### 채택 이유
- 현재 호출부가 401과 429를 구분해서 할 수 있는 일이 없음. 둘 다 해당 공급사의 처리를 실패로 기록하는 것으로 끝남
- 지금 미리 떼면 아무도 쓰지 않는 분기가 생김

#### 트레이드오프
- 재시도 정책을 도입하면 이 묶음이 부족해짐
  - 429는 백오프 후 재시도 대상이지만 401은 재시도해도 결과가 같음
  - 그 시점에 429를 별도 분류로 떼는 것이 맞다고 봄
- 즉 이 분류는 현재 소비처가 구분할 수 있는 만큼만 나눈 것임

### 같은 "본문 없음"을 통일 원칙에서 뺄 것인가

#### 배경
- A가 HTTP 200에 본문을 비워 보내는 것과, B가 `resultCode: 0000`을 주고 `data`를 null로 보내는 것은 표면상 같은 사건임

#### 검토한 선택지

| 선택지 | 얻는 것 | 잃는 것 | 판단 |
|---|---|---|---|
| (a) 두 경우를 같게 다룸 | 통일 원칙이 예외 없이 적용됨 | 의미가 다른 두 상황이 같은 결과가 됨 | 미채택 |
| (b) 성공을 선언한 주체를 기준으로 나눔 | 각 공급사의 스펙에 맞는 판정이 나옴 | 통일 표에 공급사별로 결과가 갈리는 행이 생김 | **채택** |

#### 채택 이유
- 성공을 선언한 주체가 다름
  - A는 HTTP 200 자체가 성공 선언이며, 취급 목록이 실제로 비어 있을 수 있음. 이 경우 빈 리스트로 봄
  - B는 `resultCode: 0000`으로 성공을 명시했는데 `data`가 null임. 이 경우 자기 스펙을 어긴 응답이므로 Malformed로 봄
- 통일 원칙을 기계적으로 적용하면 두 경우를 같게 다루게 되지만, 의미가 다르므로 나눔

---

### 예외 계층을 어떻게 표현할 것인가

#### 배경
- 예외를 분기해서 소비하는 코드가 이미 존재함
  - `SyncService`가 어댑터의 예외를 잡아 공급사별 결과 값으로 변환함
  - 실패 사유를 남겨야 하므로 어떤 종류의 실패였는지를 구분해야 함

#### 검토한 선택지

| 선택지                                          | 얻는 것 | 잃는 것 | 판단 |
|-------------------------------------------------|---|---|---|
| (a) 예외 클래스 하나에 사유를 enum 필드로 담음  | 새 사유가 늘어도 클래스가 안 늘어나 가벼움 | 분기 누락을 컴파일러가 잡아주지 못함 | 미채택 |
| (b) sealed 예외 계층                            | 분기에서 하위 타입 하나를 빠뜨리면 컴파일 에러로 드러남 | 새 공급사가 기존 분류에 없는 실패를 가져오면 계층을 수정해야 함 | **채택** |

#### 채택 이유
- 런타임에 "왜 이 케이스가 누락됐지"를 찾는 대신 컴파일 시점에 잡힘
- 컴파일 시점 검출이 이 결정의 목적이므로, 그것을 포기하는 (a)는 목적에 맞지 않음
- 하위 클래스는 전부 final로 두어 계층이 더 벌어지지 않게 함

#### 트레이드오프
- 새 공급사가 기존 분류에 없는 실패를 가져오면 예외 계층을 수정해야 함
  - 어댑터만 추가하면 된다는 원칙에서 벗어나는 유일한 지점임
- 그럼에도 받아들인 이유는 실패의 의미가 도메인이 알아야 하는 개념이기 때문임. 의미까지 공급사별로 두면 호출부가 공급사를 아는 상태가 되어 통일의 목적과 거리가 멀어짐

### 신규 공급사 추가 시 고칠 곳
- A를 만든 뒤 B를 추가하며 실제로 손댄 곳을 기록함

| 종류 | 내용 |
|---|---|
| 신규 클래스 | `adapter/b/` 3개 (Properties, Config, Client) |
| 기존 파일 추가 | `Supplier` enum 상수 1개 |
| 설정 추가 | `application.yaml`의 `suppliers.b` 블록 |
| 기존 로직 수정 | 0개 |

- `Supplier` enum이 늘어나는 것은 OCP 위반으로 보지 않음
  - 공급사 목록은 런타임에 발견되는 값이 아니라 코드에 명시되어야 하는 값임
  - 여기에 추가를 강제하는 것이 오히려 등록 누락을 막는 장치가 됨

#### AI에게 도움을 받아 확장 시 예상되는 변형에 대해 생각함
- 인증이 헤더가 아닌 방식인 경우
  - 해당 공급사의 Config만 수정하면 됨
- 목록이 페이징으로 오는 경우
  - 해당 공급사의 Client가 합쳐서 반환하면 되며 인터페이스는 그대로임
- 기존 분류에 없는 실패 표현을 가져오는 경우
  - 예외 계층 수정이 필요함

### 공통 코드를 만들지 않음

#### 배경
- A와 B의 Config와 Client는 코드가 거의 유사함
- 중복 코드가 발생한 것처럼 보이므로 추출 여부를 판단해야 했음

#### 검토한 선택지

| 선택지 | 얻는 것 | 잃는 것 | 판단 |
|---|---|---|---|
| (a) 공통 부모로 추출 | 중복이 사라지고 공통 개선을 한 곳에서 함 | 타임아웃 정책이 부모에 고정되고, 부모 수정이 기존 공급사 전체로 파급됨 | 미채택 |
| (b) 공급사별로 독립 유지 | 한 공급사의 변경이 다른 공급사 파일을 건드리지 않음 | 비슷한 코드가 공급사 수만큼 반복됨 | **채택** |

#### 채택 이유
1. 공급사마다 타임아웃에 대한 정책이 상이할 가능성이 있음
  - 공급사 서버마다 정책이 다른 경우 타임아웃 조건이 상이하여 각 타임아웃 설정 값이 특정 공급사의 timeout의 최소, 최대 값으로 고정되어 유동적이지 못함
2. 공통 부모의 수정이 기존 공급사로 파급됨
  - 만약 신규 공급사가 기존 코드와 다른 요구사항을 충족해야 한다면 이미 만든 공급사 코드가 영향을 받음

#### 트레이드오프
- 공통 개선이 필요해지면 공급사 수만큼 같은 수정을 반복해야 함

### 무응답을 어떤 타임아웃으로 끊을 것인가

#### 배경
- 연결은 되었는데 응답이 오지 않는 경우가 있을 수 있음
- 공급사 하나의 무응답이 나머지 처리를 막게 되므로 상한이 필요하다고 생각함

#### 검토한 선택지

| 선택지 | 얻는 것 | 잃는 것 | 판단 |
|---|---|---|---|
| (a) connect timeout만 둠 | 설정이 하나로 끝남 | 연결된 뒤 응답이 오지 않는 경우를 끊지 못함 | 미채택 |
| (b) connect timeout + read timeout | 데이터가 끊기면 호출 상한보다 일찍 에러를 냄 | 데이터가 평시보다 조금씩만 계속 들어오는 상황은 끊지 못함 | 미채택 |
| (c) connect timeout + 호출 전체 상한 | 지연의 형태와 무관하게 상한 안에서 끊김 | 데이터가 아예 오지 않는 경우에도 상한까지 기다림 | **채택** |

#### 채택 이유
- read timeout을 두었을 때 얻는 이점은 데이터가 들어오지 않을 때 호출 상한보다 일찍 에러를 던진다는 것임
- 이 이점 말고는 얻을 게 없다고 판단하여 도입하지 않음

---

### 호출 상한을 어느 단위로 걸 것인가

#### 배경
- 공급사는 하나지만 숙소 목록 조회와 재고 요금 조회는 호출 시점과 응답 크기가 다름

#### 검토한 선택지

| 선택지 | 얻는 것 | 잃는 것 | 판단 |
|---|---|---|---|
| (a) 공급사 단위 | 설정 항목이 공급사당 하나임 | 배치와 검색의 성격이 달라 한쪽에 맞추면 다른 쪽이 어긋남 | 미채택 |
| (b) 엔드포인트 단위 | 배치와 검색에 각각 맞는 값을 줌 | 설정 항목이 공급사당 두 개로 늘어남 | **채택** |

#### 채택 이유
- 공급사는 하나지만 두 엔드포인트의 성격이 다름

| | 숙소 목록 | 재고 요금 조회 |
|---|---|---|
| 호출 시점 | 하루 한 번 배치 | 고객 검색마다 |
| 응답 크기 | 보유 숙소 전체 | 숙소 50개 |
| 느릴 때 생기는 일 | 동기화가 늦어짐 | 고객이 기다림 |

- 두 API가 서로 다른 내부 시스템에 의존할 수도 있음
  - 숙소 목록 API는 정상이지만 재고 요금 조회 API가 비정상인 상황이 있을 수 있음
- 따라서 타임아웃을 거는 단위는 공급사가 아니라 공급사의 엔드포인트임

```yaml
property-list-timeout-millis: 10000
availability-timeout-millis: 500
```

- 같은 공급사가 무응답일 때 검색은 0.53초, 동기화는 10.03초에 끊기는 것을 확인함
- 재고 조회 쪽 500ms를 어떻게 정했는지는 검색 전체의 상한과 동시 호출 상한에서 계산한 값이며, 그 계산은 회복 탄력성 쪽에 기록해둠
