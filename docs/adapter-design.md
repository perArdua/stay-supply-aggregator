## 공급사 어댑터 설계

### 제약사항
- 동기화 등 도메인 계층이 의존하는 것은 공통 인터페이스(`SupplierClient`)와 자사 표준 모델(`PropertyListing`, `RoomTypeListing`)임
  - 요구사항상 공급사별 형식이 도메인 계층으로 새어 나가지 않게 경계를 두어야 함
- 공급사 전용 DTO는 해당 어댑터 클래스 내부 record로 두어 패키지 밖으로 나가면 안 됨
- 공급사 API의 실패 표현도 데이터와 마찬가지로 공급사별로 다름. 이 차이를 어댑터가 공통 예외로 변환하므로, 호출하는 쪽은 공급사별 실패 방식의 차이를 알지 못함

### 표준 모델에 supplier 필드를 두지 않음
- `PropertyListing`/`RoomTypeListing`에 출처 공급사를 나타내는 필드를 두지 않음
  - 반환한 클라이언트가 이미 출처이므로 모델이 자기 출처를 또 들고 다닐 필요가 없음
  - 필드로 두면 각 클라이언트가 자기 supplier를 매번 채워 넣어야 하고, 잘못 채워도 컴파일러가 잡지 못함
- 잃는 것: 모델 인스턴스만 보면 어느 공급사에서 왔는지 알 수 없음
  - 여러 공급사의 결과를 하나의 리스트에 섞는 순간 출처가 사라짐
  - 동기화는 공급사 단위로 순차 처리하며 결과가 섞이지 않으므로 이 구조가 성립함
- 즉 이것은 모든 모델에 적용되는 원칙이 아니라, 결과가 섞이지 않는다는 전제 위의 선택임
  - 결과를 섞어 다루는 지점이 생기면 그 지점의 모델에는 출처를 명시해야 함

### 실패 판정 통일

#### 통일하는 이유
- 공급사별로 실패를 표현하는 방식이 다르지만, 실패의 의미를 추상화하면 같음
- 통일의 목적은 호출하는 쪽이 공급사별 실패 표현을 몰라도 되게 하는 것임
  - 통일하지 않으면 호출부가 A는 HTTP 상태, B는 `resultCode`를 알고 있어야 함
  - 신규 공급사가 추가될 때마다 호출부에 해당 판정 코드를 넣어야 하며, 이는 격리의 목적과 반대임
- 실패의 종류를 타임아웃 / 공급사 측 오류 / 요청 측 오류 / 스펙 위반 응답의 네 분류로 나누고 각각을 별도 예외 클래스로 둠

| 의미 | Supplier A | Supplier B | 통일 결과 |
|---|---|---|---|
| 타임아웃 | connect/엔드포인트별 상한 초과 | 동일 | `SupplierTimeoutException` |
| 공급사 내부 오류 | HTTP 500 | 200 + `E500` | `SupplierServerException` |
| 일시적 장애 | HTTP 503 | 200 + `E503` | `SupplierServerException` |
| 잘못된 요청 | HTTP 400 | 200 + `E400` | `SupplierClientErrorException` |
| 인증 실패 | HTTP 401 | 200 + `E401` | `SupplierClientErrorException` |
| 호출 한도 초과 | HTTP 429 | 200 + `E429` | `SupplierClientErrorException` |
| 미지의 resultCode | — | 200 + 미정의 코드 | `SupplierMalformedException` |
| 성공 선언 + 본문 없음 | 빈 리스트로 처리 | `SupplierMalformedException` | 공급사별로 다름 |
| 역직렬화 실패 | 발생 시 | 발생 시 | `SupplierMalformedException` |

- 이후 요청이 공급사에 나가지 못하는 경우 두 가지가 계열에 더해짐
  - 서킷이 열려 호출하지 않은 `SupplierCircuitOpenException`
  - 커넥션 풀이 포화되어 호출하지 못한 `SupplierPoolExhaustedException`
  - 위 표는 공급사의 응답을 분류한 것인데 이 둘은 응답 자체가 없으므로 넣지 않음

#### 같은 "본문 없음"을 다르게 다룬 이유
- 성공을 선언한 주체가 다름
  - A는 HTTP 200 자체가 성공 선언이며, 취급 목록이 실제로 비어 있을 수 있음
    - 이 경우 빈 리스트로 봄
  - B는 `resultCode: 0000`으로 성공을 명시했는데 `data`가 null임
    - 이 경우 자기 스펙을 어긴 응답이므로 Malformed로 봄
- 통일 원칙을 기계적으로 적용하면 두 경우를 같게 다루게 되지만, 의미가 다르므로 나눔

#### 네 분류로 묶으면서 잃은 것
- A의 401과 429가 같은 `SupplierClientErrorException`이 됨
- 두 가지는 실제 대응이 다름. 401은 인증 문제라 사람이 고쳐야 하고, 429는 기다리면 풀림
- 그럼에도 묶은 이유는 현재 호출부가 둘을 구분해서 할 수 있는 일이 없기 때문임. 둘 다 해당 공급사의 처리를 실패로 기록하는 것으로 끝남
- 재시도 정책을 도입하면 이 묶음이 부족해짐
  - 429는 백오프 후 재시도 대상이지만 401은 재시도해도 결과가 같음
  - 그 시점에 429를 별도 분류로 떼는 것이 맞다고 봄. 지금 미리 떼면 아무도 쓰지 않는 분기가 생김
- 즉 이 분류는 현재 소비처가 구분할 수 있는 만큼만 나눈 것임

### 예외 계층을 sealed로 둔 이유
- 예외를 분기해서 소비하는 코드가 이미 존재함
  - `SyncService`가 어댑터의 예외를 잡아 공급사별 결과 값으로 변환함
  - 실패 사유를 남겨야 하므로 어떤 종류의 실패였는지를 구분해야 함
- sealed로 두면 그 분기에서 하위 타입 하나를 빠뜨렸을 때 컴파일 에러로 드러남
  - 런타임에 "왜 이 케이스가 누락됐지"를 찾는 대신 컴파일 시점에 잡힘
  - 하위 클래스는 전부 final로 두어 계층이 더 벌어지지 않게 함

#### 이 선택의 비용
- 새 공급사가 기존 분류에 없는 실패를 가져오면 예외 계층을 수정해야 함
  - 어댑터만 추가하면 된다는 원칙에서 벗어나는 유일한 지점임
- 실패의 의미는 도메인이 알아야 하는 개념이므로 의미까지 공급사별로 두게 되면 호출부가 공급사를 아는 상태가 되어 통일의 목적과는 거리가 멀다고 생각함

#### AI가 제안했지만 받아들이지 않은 대안
- 예외 클래스 하나에 사유를 enum 필드로 담는 방식
  - 새 사유가 늘어도 클래스가 안 늘어나 가벼움
  - 대신 분기 누락을 컴파일러가 잡아주지 못함
  - 컴파일 시점 검출이 sealed를 택한 이유여서 맞지 않다고 판단함

### 신규 공급사 추가 시 고칠 곳
- A를 만든 뒤 B를 추가하며 실제로 손댄 곳을 기록함

| 종류 | 내용 |
|---|---|
| 신규 클래스 | `adapter/b/` 3개 (Properties, Config, Client) |
| 기존 파일 추가 | `Supplier` enum 상수 1개 |
| 설정 추가 | `application.yaml`의 `supplier.b` 블록 |
| 기존 로직 수정 | 0개 |

- `Supplier` enum이 늘어나는 것은 OCP 위반으로 보지 않음
  - 공급사 목록은 런타임에 발견되는 값이 아니라 코드에 명시되어야 하는 값임
  - 여기에 추가를 강제하는 것이 오히려 등록 누락을 막는 장치가 됨

#### AI에게 도움을 받아 확장 시 예상되는 변형에 대해 생각함
- 인증이 헤더가 아닌 방식인 경우
  - 해당 공급사의 Config만 수정하면 됨
- 목록이 페이징으로 오는 경우
  - 해당 공급사의 Client가 합쳐서 반환하면 되며 인터페이스는 그대로임
- 기존 네 분류에 없는 실패 표현을 가져오는 경우
  - 예외 계층 수정이 필요함

### 공통 코드를 만들지 않음

#### 판단이 어려웠던 지점
- A와 B의 Config와 Client는 코드가 거의 유사함
- 중복 코드가 발생한 것처럼 보임 그럼에도 불구하고 추출하지 않기로 함

#### 추출하지 않은 이유
1. 공급사마다 타임아웃에 대한 정책이 상이할 가능성이 있음
  - 공급사 서버마다 정책이 다른 경우 타임아웃 조건이 상이하여 각 타임아웃 설정 값이 특정 공급사의 timout의 최소, 최대 값으로 고정되어 유동적이지 못함
2. 공통 부모의 수정이 기존 공급사로 파급됨
  - 만약 신규 공급사가 기존 코드와 다른 요구사항을 충족해야 한다면 이미 만든 공급사 코드가 영향을 받음

#### 얻는 것과 잃는 것
| | 내용                                                                     |
|---|--------------------------------------------------------------------------|
| 얻는 것 | 한 공급사의 변경이 다른 공급사 파일을 건드리지 않음 |
| 잃는 것 | 비슷한 코드가 공급사 수만큼 반복됨. 공통 개선 시 모든 곳을 고쳐야 함     |

### 타임아웃 구성
- connect timeout과 호출 상한을 사용함
- 호출 상한을 사용한 이유
  - 연결은 되었는데 응답이 오지 않는 경우가 있을 수 있음
  - 공급사 하나의 무응답이 나머지 처리를 막게 되므로 timeout 상한이 필요하다고 생각함
- 호출 상한은 공급사가 아니라 엔드포인트 단위로 둠
  - 숙소 목록은 배치로 부르고 재고 조회는 검색마다 부르므로 성격이 다름
  - 근거는 회복 탄력성 문서에 정리함
- read timeout을 쓰지 않은 이유
  - 데이터가 평시보다 조금씩만 계속 들어오는 상황은 read timeout으로 해결할 수 없음
  - read timeout을 두었을 때 얻는 이점은 데이터가 들어오지 않을 때 호출 상한보다 일찍 에러를 던진다는 것임
  - 이 이점 말고는 얻을 게 없다고 판단하여 도입하지 않음
