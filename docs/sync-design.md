## 숙소 목록 동기화 설계

### 동기화 트리거

| 트리거                    | 구현                          | 시점                                  |
|---------------------------|-------------------------------|---------------------------------------|
| 서버 시작시 조건부로 실행 | `SyncStartupRunner`           | 앱 시작 시 매핑이 비어 있을 때만 실행 |
| 주기 실행                 | `SyncScheduler` | 매일 04:00                            |
| 수동 실행                 | `POST /internal/sync`         | 호출 시                               |

---

### 서버 시작 시 동기화를 언제 돌릴 것인가

#### 배경
- 앱이 기동할 때 매핑을 채울지 정해야 함
- 매핑이 비면 검색이 빈 결과만 반환함. 대상 숙소 코드를 하나도 모르기 때문임

#### 검토한 선택지

| 선택지 | 얻는 것 | 잃는 것 | 판단 |
|---|---|---|---|
| (a) 시작할 때마다 무조건 실행 | 목록이 항상 최신에 가까움 | 재배포 1회당 호출 1회가 늘고, 인스턴스를 3대로 늘리면 3회가 됨 | 미채택 |
| (b) 시작 시 실행하지 않음 | 기동이 공급사 상태에 묶이지 않음 | 매핑이 빈 상태로 떠서 다음 스케줄까지 검색이 성립하지 않음 | 미채택 |
| (c) 매핑이 비어 있을 때만 실행 | 기능이 성립하지 않는 상태만 막고 평시 호출은 늘리지 않음 | 매핑이 낡았지만 비어 있지는 않은 경우는 스케줄을 기다려야 함 | **채택** |

#### 채택 이유
- (a)로 얻는 것은 "그 사이에 바뀌었을지 모르는 목록"인데 이는 04:00 스케줄이 처리함
- 배포 빈도가 높을수록 (a)의 손해가 커지는 구조임
- 매핑이 비는 것은 기능 자체가 성립하지 않는 상태이므로 이 경우에만 채움
- 매핑 유무에 대한 판정은 매핑 테이블 전체 건수 기준이며 공급사별로 나누지 않음

---

### 동기화 주기를 얼마로 둘 것인가

#### 배경
- 숙소 목록이 바뀌는 사건은 공급사의 신규 계약 및 계약 종료라고 생각했고, 이는 실시간성이 필요한 종류가 아님
- 공급사의 레이트 리밋 값이 스펙에 주어지지 않았음

#### 검토한 선택지

| 선택지 | 얻는 것 | 잃는 것 | 판단 |
|---|---|---|---|
| (a) 1시간 주기 | 노출 지연이 최대 1시간으로 줄어듦 | 호출량이 24배가 되고 공급사 수만큼 곱해짐 | 미채택 |
| (b) 하루 1회 주기 | 호출량이 공급사당 하루 1회로 고정됨 | 노출 지연이 최대 24시간임 | **채택** |
| (c) 주 1회 주기 | 호출량이 공급사당 주 1회로 고정됨 | 노출 지연이 최대 7일임| 미채택 |

#### 채택 이유
- 요청 리밋을 모르는 상태에서 호출량을 24배로 먼저 올릴 이유가 없다고 판단함
- 급한 경우는 수동 실행으로 처리 가능함
- 04:00은 트래픽이 제일 낮은 시간대로 추측되며, 동기화의 쓰기 부하가 검색 트래픽과 겹치지 않음

#### 트레이드오프
- 공급사가 숙소를 추가해도 최대 하루 동안 검색에 나오지 않음
- 값은 `sync.cron` 설정 값으로 빼뒀으므로 필요해지면 배포 없이 조정 가능함

---

### 수동 실행
- 수동 실행이 필요한 경우 다음 스케줄링이 동작하는 시간을 기다리지 않기 위해 넣음
- 동작 확인 수단으로도 사용함
- `/internal` 경로에 두어 고객용 API가 아님을 경로로 드러냄
- 인증 및 인가는 범위 밖이라 걸지 않음. 실제 운영이라면 보안 조치가 필요함

---

### 같은 상품은 항상 같은 내부 식별자를 갖도록 멱등성이 필요함
- 요구사항: 동기화가 여러 번 돌아도, 스케줄과 수동이 겹쳐도, 인스턴스가 여러 대여도 이미 발급한 내부 식별자가 바뀌면 안 됨
- 보장 수단은 두 가지임
    - UNIQUE 제약 — `(supplier, supplier_code)` / `(property_id, supplier_room_code)`
    - upsert — 존재하면 갱신, 없으면 삽입. 새 행을 만들지 않으므로 PK가 유지됨
- 객실 타입 코드는 숙소 안에서만 유일하므로 매핑 키에 숙소가 함께 들어감

#### upsert-then-select를 사용한 이유
- `INSERT ... ON DUPLICATE KEY UPDATE`가 갱신된 행의 PK를 돌려주지 않음
- 객실 타입 매핑을 넣으려면 부모인 내부 숙소 식별자가 반드시 필요하므로, UPSERT를 수행한 뒤 SELECT를 수행함

---

### 매핑 키의 대소문자를 구분할 것인가

#### 배경
- 매핑 키는 공급사가 준 문자열 코드임
- MySQL의 기본 collation은 대소문자를 구분하지 않음

#### 검토한 선택지

| 선택지 | 얻는 것 | 잃는 것 | 판단 |
|---|---|---|---|
| (a) 기본 collation | 공급사가 표기를 흔들어도 같은 상품으로 붙음 | 공급사가 다른 상품으로 취급하는 두 코드가 한 행으로 합쳐짐 | 미채택 |
| (b) `COLLATE utf8mb4_bin` | 공급사가 준 코드를 준 그대로 구분함 | 공급사가 같은 상품의 표기를 바꾸면 다른 상품으로 잡힘 | **채택** |

#### 채택 이유
- 공급사가 `DLX-TWN`과 `dlx-twn`을 다른 상품으로 취급할 수도 있기 때문에 대소문자를 구별해야 한다고 생각함
- 합쳐서 틀리면 서로 다른 두 상품이 하나의 내부 식별자를 갖게 되어 되돌리기 어려움

---

### 트랜잭션 경계를 어느 단위로 둘 것인가

#### 배경
- 동기화 한 번이 여러 공급사의 매핑 upsert와 비활성화 스윕(sweep)을 수행함
- 공급사 호출은 트랜잭션 밖에서 해야 함. 응답을 기다리는 동안 DB 커넥션과 잠금을 붙잡게 되기 때문임

#### 검토한 선택지

| 선택지 | 얻는 것 | 잃는 것 | 판단 |
|---|---|---|---|
| (a) 숙소 단위 등 더 작게 | 락 점유 구간이 짧아짐 | 중간 실패 시 `last_synced_at`이 일부만 갱신되어, 멀쩡한 숙소가 사라진 것으로 인식될 수 있음 | 미채택 |
| (b) 공급사 하나 단위 | 한 공급사의 upsert와 스윕이 전부 커밋되거나 전부 롤백됨 | 공급사 하나의 매핑이 클수록 트랜잭션이 길어짐 | **채택** |
| (c) 동기화 전체를 하나로 | 전체가 한 번에 일관됨 | A의 실패가 B의 결과까지 롤백시켜 공급사가 서로 독립이 아니게 됨 | 미채택 |

#### 채택 이유
- `MappingWriter`가 `@Transactional`을 갖고 공급사 하나의 매핑 upsert 전체와 비활성화 스윕이 그 안에서 끝남
- (a)는 스윕과 upsert가 갈라져 부분 갱신 상태를 만들 수 있음
- (c)는 공급사가 서로 독립이어야 한다는 전제를 깸

#### 구현상 주의
- 호출부와 저장 구간을 다른 클래스로 나눔. 같은 클래스 안에서 부르면 프록시를 타지 않아 트랜잭션이 걸리지 않음

#### 예외를 값으로 바꾸는 지점
- `MappingWriter`는 예외를 던짐 — 잡아서 값으로 반환하면 정상 종료로 보여 롤백이 걸리지 않음
- `SupplierSyncExecutor`도 예외를 던짐 — 공급사 호출이 실패하면 저장 구간을 부르지 않아야 함
- `SyncService`가 잡아 `SyncResult` 값으로 변환함 — 공급사 루프의 경계이며, 여기서 잡아야 A의 실패가 B의 실행을 막지 않음
- 결과는 공급사별 성공/실패 목록이 됨. 전부 성공 아니면 전부 실패가 아니라 건별 결과를 모아 돌려주는 형태임

---

### 사라진 숙소를 어떻게 지울 것인가

#### 배경
- 공급사가 숙소를 목록에서 빼도 upsert만으로는 알 수 없음. 응답에 없는 것은 갱신되지 않을 뿐임
- 탐지 방식은 두 단계임
    1. 공급사 목록을 전부 upsert하며 `last_synced_at`을 이번 실행 시각으로 찍음
    2. 같은 공급사의 행 중 `last_synced_at`이 이번 실행 시각보다 오래된 것을 이번 목록에 없던 것으로 봄
- 객실 타입은 부모 숙소를 통해 JOIN해 같은 판정을 받음

#### 검토한 선택지

| 선택지 | 얻는 것 | 잃는 것 | 판단 |
|---|---|---|---|
| (a) 물리 삭제 | 테이블에 죽은 행이 남지 않음 | 이미 외부로 나간 내부 식별자가 무엇이었는지 알 수 없게 되고, 복원 시 새 식별자가 발급되어 멱등성 요구가 깨짐 | 미채택 |
| (b) `active = false`로 soft delete | 식별자와 이력이 남아 복원해도 같은 식별자를 씀 | 행이 계속 쌓이고 조회에 `active` 조건이 항상 붙음 | **채택** |

#### 채택 이유
- 내부 식별자는 이미 외부로 나갔을 수 있어 지우면 그것이 무엇이었는지 알 수 없게 됨
- 물리 삭제했다가 다시 복원하는 경우 새 식별자가 발급되어 멱등성 요구가 깨짐

---

### 빈 목록 응답을 어떻게 다룰 것인가

#### 배경
- 공급사가 성공 응답으로 빈 목록을 줬을 때 해석은 두 가지를 생각할 수 있음
    - 정말 취급 숙소가 없음
    - 공급사 쪽 문제로 목록이 비어서 옴
- 두 해석을 구분할 방법이 없음

#### 검토한 선택지

| 선택지 | 얻는 것 | 잃는 것 | 판단 |
|---|---|---|---|
| (a) 그대로 받아들임 | 공급사가 정말 철수한 경우 자동 반영됨 | 공급사 쪽 문제였다면 그 공급사의 모든 숙소가 비활성화되고 검색 결과가 통째로 사라짐. 복구는 다음 정상 동기화까지 안 됨 | 미채택 |
| (b) 실패로 다룸 | 기존 매핑이 그대로 남아 검색이 유지됨 | 공급사가 정말 전부 철수한 경우 자동 반영되지 않고 사람이 개입해야 함 | **채택** |

#### 채택 이유
- 두 해석을 구분할 방법이 없으므로 피해가 큰 쪽을 막기로 함
- 목록이 비었으면 `SupplierSyncExecutor`가 `EmptyPropertyListException`을 던져 저장 구간을 아예 호출하지 않음
- 빈 목록을 걸러내지 못하면 되돌릴 방법이 없음
    - 공급사 호출이 트랜잭션 안에 있던 동안에는 스윕이 돌아도 롤백이 되돌려 주었음
    - 지금은 저장 구간에 들어가는 순간 트랜잭션이 시작되므로, 빈 목록으로 들어가면 스윕 결과가 그대로 커밋됨

#### 트레이드오프
- 공급사가 정말 전부 철수한 경우 자동 반영되지 않고 사람이 개입해야 함
