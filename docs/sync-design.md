## 숙소 목록 동기화 설계

### 동기화 트리거

| 트리거                    | 구현                          | 시점                                  |
|---------------------------|-------------------------------|---------------------------------------|
| 서버 시작시 조건부로 실행 | `SyncStartupRunner`           | 앱 시작 시 매핑이 비어 있을 때만 실행 |
| 주기 실행                 | `SyncScheduler` | 매일 04:00                            |
| 수동 실행                 | `POST /internal/sync`         | 호출 시                               |

#### 서버 시작시 무조건 실행하지 않는 이유
- 매핑이 이미 있을 때 서버를 시작할 때마다 호출하면 재배포 1회당 호출 1회가 늘고, 인스턴스를 3대로 늘리면 3회가 됨
- 얻는 것은 "그 사이에 바뀌었을지 모르는 목록"인데 이는 04:00 스케줄이 처리함
- 배포 빈도가 높을수록 손해가 커지는 구조라 채택하지 않음

#### 매핑이 비어 있을 때만 도는 이유
- 매핑이 비면 검색이 빈 결과만 반환함. 대상 숙소 코드를 하나도 모르기 때문임
- 기능 자체가 성립하지 않는 상태이므로 이 경우에만 채움
- 매핑 유무에 대한 판정은 매핑 테이블 전체 건수 기준이며 공급사별로 나누지 않음

#### 주기를 하루로 둔 이유
- 숙소 목록이 바뀌는 사건은 공급사의 신규 계약 및 계약 종료라고 생각했고, 이는 실시간성이 필요한 종류가 아님
- 1시간으로 줄이면 노출 지연이 최대 24시간에서 1시간으로 줄지만, 호출량이 24배가 되고 공급사 수만큼 곱해짐
- 공급사 레이트 리밋 값이 스펙에 없고, 리밋을 모르는 상태에서 호출량을 24배로 먼저 올릴 이유가 없다고 판단함
- 급한 경우는 수동 실행으로 처리 가능함
- 04:00은 트래픽이 제일 낮은 시간대로 추측되며, 동기화의 쓰기 부하가 검색 트래픽과 겹치지 않음
- 값은 sync.cron 설정 값으로 빼뒀으므로 필요해지면 배포 없이 조정 가능함

#### 수동 실행
- 수동 실행이 필요한 경우 다음 스케줄링이 동작하는 시간을 기다리지 않기 위해 넣음
- 동작 확인 수단으로도 사용함
- /internal 경로에 두어 고객용 API가 아님을 경로로 드러냄
- 인증 및 인가는 범위 밖이라 걸지 않음. 실제 운영이라면 보안 조치가 필요함

---

### 같은 상품은 항상 같은 내부 식별자를 갖도록 멱등성이 필요함
- 요구사항: 동기화가 여러 번 돌아도, 스케줄과 수동이 겹쳐도, 인스턴스가 여러 대여도 이미 발급한 내부 식별자가 바뀌면 안 됨
- 보장 수단은 두 가지임
    - UNIQUE 제약 — `(supplier, supplier_code)` / `(property_id, supplier_room_code)`
    - upsert — 존재하면 갱신, 없으면 삽입. 새 행을 만들지 않으므로 PK가 유지됨
- 객실 타입 코드는 숙소 안에서만 유일하므로 매핑 키에 숙소가 함께 들어감
- `COLLATE utf8mb4_bin`을 쓴 이유
    - 기본 설정은 대소문자를 구분하지 않음
    - 공급사가 `DLX-TWN`과 `dlx-twn`을 다른 상품으로 취급할 수도 있기 때문에 대소문자를 구별해야 한다고 생각함

#### upsert-then-select를 사용한 이유
- `INSERT ... ON DUPLICATE KEY UPDATE`가 갱신된 행의 PK를 돌려주지 않음
- 객실 타입 매핑을 넣으려면 부모인 내부 숙소 식별자가 반드시 필요하므로, UPSERT를 수행한 뒤 SELECT를 수행함

### 트랜잭션 경계는 공급사 별로 1개면 된다고 판단함
- `SupplierSyncExecutor`가 `@Transactional`을 갖고 공급사 하나의 처리 전체가 그 안에서 끝남
- 더 작은 단위로 쪼개지 않은 이유
    - 중간 실패 시 `last_synced_at`이 일부만 갱신되어, 멀쩡한 숙소가 사라진 것으로 인식이 될 수도 있음
- 더 큰 단위로 쪼개지 않은 이유
    - 공급사는 서로 독립이어야 함

#### 예외를 값으로 바꾸는 지점
- `SupplierSyncExecutor`는 예외를 던짐 — 잡아서 값으로 반환하면 정상 종료로 보여 롤백이 걸리지 않음
- `SyncService`가 잡아 `SyncResult` 값으로 변환함 — 공급사 루프의 경계이며, 여기서 잡아야 A의 실패가 B의 실행을 막지 않음
- 결과는 공급사별 성공/실패 목록이 됨. 전부 성공 아니면 전부 실패가 아니라 건별 결과를 모아 돌려주는 형태임

---

### 사라진 숙소 처리
- 문제: 공급사가 숙소를 목록에서 빼도 upsert만으로는 알 수 없음. 응답에 없는 것은 갱신되지 않을 뿐임
- 방식
    1. 공급사 목록을 전부 upsert하며 `last_synced_at`을 이번 실행 시각으로 찍음
    2. 같은 공급사의 행 중 `last_synced_at`이 이번 실행 시각보다 오래된 것을 `active = false`로 바꿈
- 객실 타입은 부모 숙소를 통해 JOIN해 같은 판정을 받음

#### 물리 삭제가 아니라 soft delete인 이유
- 내부 식별자는 이미 외부로 나갔을 수 있어 지우면 그것이 무엇이었는지 알 수 없게 됨
- 물리삭제 했다가 다시 복원하는 경우 새 식별자가 발급되어 멱등성 요구가 깨짐

---

### 빈 목록 응답을 실패로 다루는 이유
- 공급사가 성공 응답으로 빈 목록을 줬을 때 해석은 두 가지를 생각할 수 있음
    - 정말 취급 숙소가 없음
    - 공급사 쪽 문제로 목록이 비어서 옴
- 그대로 받아들이면 `last_synced_at`을 기준으로 그 공급사의 모든 숙소를 비활성화하고, 검색 결과가 통째로 사라짐. 복구는 다음 정상 동기화까지 안 됨
- 두 해석을 구분할 방법이 없으므로 피해가 큰 쪽을 막기로 함
- `SupplierSyncExecutor`가 `EmptyPropertyListException`을 던져 해당 공급사 트랜잭션을 롤백함. 기존 매핑은 그대로 남음
- 잃는 것: 공급사가 정말 전부 철수한 경우 자동 반영되지 않고 사람이 개입해야 함.

### 한계

#### 트랜잭션 안에서 HTTP를 호출함
- `SupplierSyncExecutor`가 `@Transactional` 안에서 공급사를 호출하므로 응답을 기다리는 동안 DB 커넥션이 잡혀 있음
- 구조적으로 옳지 않다고 판단하기에 개선하기로 결정함
- 공급사 호출을 트랜잭션 밖으로 빼고 받아온 목록만 트랜잭션 안으로 넘기는 방식을 생각 중
