## 연동 견고성 설계

### 실패를 다루는 층
- 외부 연동은 실패하므로 실패를 전제로 설계해야 함
- 실패를 감지하고 끊는 지점이 층마다 다름

| 층 | 장치 | 무엇을 막는가                              |
|---|---|--------------------------------------------|
| 호출 하나 | 호출 상한 | 응답이 오지 않는 호출이 무한정 기다리는 것 |
| 검색 요청 하나 | 검색 상한 | 청크 수에 비례해 응답 시간이 늘어나는 것   |
| 요청과 요청 사이 | 서킷 브레이커 | 죽은 공급사에 계속 호출을 보내는 것        |
| 응답 | 부분 실패 허용 | 한 공급사의 실패가 전체 실패가 되는 것     |

---

### 타임아웃

#### 엔드포인트마다 다른 값을 둠
- 공급사는 하나지만 숙소 목록 조회와 재고 요금 조회의 성격이 다름

| | 숙소 목록 | 재고 요금 조회 |
|---|---|---|
| 호출 시점 | 하루 한 번 배치 | 고객 검색마다 |
| 응답 크기 | 보유 숙소 전체 | 숙소 50개 |
| 느릴 때 생기는 일 | 동기화가 늦어짐 | 고객이 기다림 |

- 두 API가 서로 다른 내부 시스템에 의존할 수도 있음
  - 숙소 목록 API는 정상이지만 재고 요금 조회 API가 비정상인 상황이 있을 수 있음
- 따라서 타임아웃과 서킷을 거는 단위는 공급사가 아니라 공급사의 엔드포인트임

```yaml
property-list-timeout-millis: 10000
availability-timeout-millis: 500
```

- 같은 공급사가 무응답일 때 검색은 0.53초, 동기화는 10.03초에 끊김
- 다만 검색 쪽 값은 청크가 1개인 규모 기준이며, 숙소가 늘면 서킷과 검색 상한이 함께 관여함

### 검색 요청 전체의 상한

#### 결론부터
- 값 셋을 정했고 그 결과로 한 번의 검색이 다룰 수 있는 숙소 수가 정해짐

| 값 | 정한 값 | 어떻게 정했는가 |
|---|---|---|
| 검색 상한 | 2000ms | 가정 |
| 동시 호출 상한 | 10 | 가정 |
| 호출 상한 | 500ms | 앞의 둘에서 계산한 뒤 조정 |
| 다룰 수 있는 숙소 수 | 1500개 | 위 셋에서 따라 나온 결과 |

- 숙소 1500개를 목표로 놓고 값을 맞춘 것이 아님. 값을 정하고 나니 범위가 그렇게 정해진 것임
- 보유 숙소가 그보다 많으면 뒤쪽 청크가 검색 상한에 잘려 결과가 덜 완전해짐

#### 정하는 순서
1. 우리 쪽 고정 비용을 측정함. 예산에서 이 값을 먼저 빼야 하기 때문임
2. 검색 상한을 정함. 이 시스템에서 도출되지 않아 가정으로 둠
3. 동시 호출 상한을 정함. 이것도 도출되지 않아 가정으로 둠
4. 앞의 값들에서 호출 상한을 계산하고, 계산값이 공급사에게 지나치게 짧다고 보아 조정함
5. 조정한 결과로 다룰 수 있는 숙소 수가 정해짐

#### 다룰 수 있는 숙소 수는 검색 상한, 동시 호출 상한, 호출 상한에 따라 달라짐
- 검색 하나가 만드는 공급사 호출이 여러 개임
  - 재고 조회 API가 한 번에 숙소 코드를 50개까지 받으므로 보유 숙소를 50개씩 청크로 나눔
  - 숙소가 4000개면 공급사당 청크가 80개가 됨
- 청크를 한꺼번에 다 보내지 않고 동시 호출 상한만큼만 보냄
  - 상한이 10이면 진행 중인 호출이 항상 10개 이하로 유지됨
  - 청크 80개를 10개씩 처리하면 8번에 나누어 보내게 됨
- 한 번 보낼 때 걸리는 시간은 길어야 호출 상한만큼임
- 따라서 최악의 경우 공급사 호출에 드는 시간은 나누어 보내는 횟수에 호출 상한을 곱한 값임
- 여기에 우리 쪽 고정 비용을 더한 것이 검색 전체에 걸리는 시간이고, 그것이 검색 상한 안에 들어와야 함
- 정리하면 검색 상한에서 고정 비용을 빼고 호출 상한으로 나누면 몇 번까지 나누어 보낼 수 있는지가 나오며, 거기에 동시 호출 상한과 청크당 숙소 수를 곱하면 다룰 수 있는 숙소 수가 나옴

#### 청크는 순차적으로 실행되는 것이 아님
- `flatMapSequential`의 동시 호출 상한은 진행 중인 호출 개수의 상한임
  - 호출 하나가 끝나면 그 자리에 즉시 다음 청크가 들어감
  - 청크 10개가 모두 끝나기를 기다렸다가 다음 10개를 보내는 것이 아님
- 다만 정하려는 것이 최악의 경우 상한이므로 청크 10개가 모두 끝나기를 기다렸다가 다음 10개를 보내는 것이라고 가정함

#### 우리 쪽 고정 비용은 측정할 수 있음
- 공급사 호출을 뺀 구간을 제외하여 30회 측정 했고 기준 지표는 p95임

| 구간 | 숙소 3개 | 숙소 4000개 |
|---|---|---|
| 컨트롤러 진입부터 매핑 조회 완료 | 2.7ms | 20.4ms |
| 마지막 청크 도착부터 응답 완료 | 1.3ms | 2.5ms |
| 합 | 4.0ms | 22.9ms |

- 매핑 조회가 숙소 수에 비례해 늘어남
  - 이 구간은 동기 JDBC라 요청 스레드가 묶임
  - 지금 규모에서는 병목이 아니지만 숙소 수가 더 늘어나면 튜닝이 필요할 수 있음
- 계산에서는 23ms로 잡음

#### 검색 상한은 최악의 경우 상한이며 평균이 아님
- 정상 경로에서는 발동하지 않음
- 최악의 경우에 고객을 얼마나 붙잡아 둘 것인가임
- 장애 상황에서 고객은 최대 2초까지 기다릴 수 있다고 판단함
- 시간이 길어지면 고객은 서비스에서 이탈하고 다른 일을 하러갈 수도 있음

#### 동시 호출 상한은 10으로 가정함
- 한 공급사에 동시에 진행 중인 호출 수의 상한임
- 만약 상한이 없다면 공급사가 보유한 숙소 수에 비례하여 호출이 만들어짐
  - 숙소가 4000개 있다고 했을 때, 청크가 80개이므로 한 번에 80개의 요청이 만들어지는 것임
  - 공급사가 2개면 160개임
- 진행 중인 호출 하나가 커넥션 하나를 점유함
- 커넥션 풀이 감당하지 못할 정도로 요청이 많이 생성되면 요청은 대기하게 되는데, 이 대기 시간이 호출 상한에 포함되는 문제가 있음
  - 이 경우 공급사는 멀쩡한데 TIMEOUT으로 기록되어 실패 원인을 잘못 기록하게 됨
- 공급사 관점에서도 한 번에 많은 요청이 몰리는 것은 부담될 것임
- 다만 현 상황에서는 공급사의 호출 한도를 모르고 커넥션 풀도 Mock 환경에서는 제약이 되지 않기 때문에 임의로 10으로 정함
  - 이 값은 공급사 별로 상한을 둔 것이므로 전역 상한은 공급사 수와 이 값을 곱한 값이 됨

#### 호출 상한은 계산한 뒤 조정함
- 검색 상한 2000ms에서 고정 비용 23ms를 빼면 공급사 호출에 쓸 수 있는 시간이 1977ms임
- 숙소 4000개를 다루려면 청크 80개를 10개씩 8번에 나누어 보내야 하므로, 한 번에 허용되는 시간은 1977을 8로 나눈 247ms임
- 247ms를 그대로 쓰지 않았음
  - 측정할 때마다 어느정도 달라지기 때문임 
  - 공급사의 실제 응답 시간을 모르는 상태에서 247ms는 지나치게 짧다고 생각함
  - 이보다 느린 공급사의 정상 응답을 타임아웃으로 처리하게 됨
- 그래서 여유 있게 500ms로 올림
  - 그 대신 다룰 수 있는 숙소 수가 4000개에서 1500개로 줄어듦

#### 검색 상한을 줄이면 보낼 수 있는 숙소 수가 줄어듦

| 검색 상한 | 나누어 보내는 횟수 | 숙소 |
|---|---|---|
| 5000ms | 9 | 4500개 |
| 3000ms | 5 | 2500개 |
| 2000ms | 3 | 1500개 |
| 1000ms | 1 | 500개 |

- 이 구조에서는 고객 대기 시간, 보낼 수 있는 숙소 수, 공급사 부하 중 두 가지를 선택해야 함
  - 고객 대기 시간은 짧아야 하고, 공급사 부하는 적어야 한다고 우선적으로 생각함
  - 보낼 수 있는 숙소 수는 캐시를 두면 늘릴 수 있지만 캐시는 적용하지 않음

#### 캐시를 적용하지 않은 이유
- 검색마다 보유 숙소 전체를 공급사에 실시간으로 물어보는 구조이기 때문에 캐시를 두면 고객 대기 시간, 보낼 수 있는 숙소 수, 공급사 부하 세가지를 모두 잘 다룰 수 있음
- 도입한다면 정책적으로는 TTL은 어떻게 둘지, 원본과의 정합성 허용 오차를 정해야 함
  - 정책적인 부분을 정해 본 경험이 없기 때문에 Mock 환경이더라도 도입하지 않는게 맞다고 생각함 
- 기술적으로는 캐시스탬피드, 캐시 관통 등의 문제를 대비해야 함

#### 검색 상한을 두는 이유
- 완료 조건을 모든 호출이 끝나는 시점으로 두면 응답 시간이 가장 느린 호출에 좌지우지됨
- 상한을 두면 청크 수와 무관하게 응답 시간이 고정됨

#### 잘린 청크는 TIMEOUT으로 집계함
- 검색 상한에 걸려 도착하지 못한 청크는 응답에서 `TIMEOUT`으로 나감
  - 청크의 결과를 받지 못했기 때문임

#### 얻는 것과 잃는 것
| | 내용 |
|---|---|
| 얻는 것 | 청크 수와 무관하게 응답 시간의 상한이 고정됨 |
| 잃는 것 | 커버 범위를 넘는 규모에서는 뒤쪽 청크가 잘려 결과가 덜 완전해짐 |

- 응답이 느린 것보다 결과가 덜 완전한 쪽이 낫다고 판단함
- 응답이 느린 것보다 결과가 덜 완전한 쪽이 낫다고 판단함
- 고객에게 빨리 응답해야 하기 때문임

### 서킷 브레이커

#### 도입한 이유
- 서킷이 없으면 공급사 A가 죽어 있어도 검색할 때마다 청크를 계속 보냄
- 두 가지를 막기 위해 도입
  - 고객이 죽은 공급사를 기다리는 시간
  - 죽은 공급사로 나가는 무의미한 호출

#### 검색 상한과 역할이 다름
| | 검색 상한 | 서킷 |
|---|---|---|
| 보는 것 | 검색 시작 후 흐른 시간 | 청크 호출의 실패 비율 |
| 상태가 남는 범위 | 요청 안 | 요청 사이 |

- 공급사가 완전히 죽으면 서킷에 의해 검색 상한은 발동하지 않음
- 검색 상한이 필요한 상황은 서킷이 열리지 않는 경우임
  - 실패율이 임계값 아래로 유지되면서 응답만 계속 느린 상태

#### 청크 단위에 걺
- 실패를 세는 단위가 청크여야 80개 중 몇 개 실패라는 값이 의미를 가짐
- 공급사 단위로 걸면 한 번의 성공 또는 실패로만 집계되어 임계값이 뜻을 잃음
- 서킷 인스턴스 이름을 `A-availability` 형태로 둠

#### 애노테이션이 아니라 연산자를 씀
- `@CircuitBreaker`와 fallback 방식을 검토했으나 두 가지가 걸림
  - fallback이 실행되면 예외가 상위로 전파되지 않음 즉, 예외 종류를 분기하는 switch까지 도달하지 못하므로, 경우를 빠짐없이 다뤘는지 컴파일러가 검사해주던 것이 무의미해짐
  - 서킷이 어디에 걸렸는지 코드에 드러나지 않음
- `CircuitBreakerOperator`를 `transformDeferred`로 거는 방식은 예외가 그대로 올라와 기존 처리 경로를 탐

#### 설정값과 근거
| 값 | 근거                                                              |
|---|-------------------------------------------------------------------|
| `slidingWindowType: COUNT_BASED` | 호출 개수로 셈                                                    |
| `slidingWindowSize: 10` | 동시 호출 상한과 동일                                             |
| `minimumNumberOfCalls: 10` | 이보다 작으면 처음 나간 호출들의 결과가 도착하기 전에 판정하게 됨 |
| `failureRateThreshold: 50` | 결과를 덜 받더라도 빨리 끝내는 쪽                                 |
| `permittedNumberOfCallsInHalfOpenState: 1` | 아래에 적어 두었음                                                |
| `waitDurationInOpenState: 30s` | 도출된 값이 아님                                                  |
| `automaticTransitionFromOpenToHalfOpenEnabled: true` | 아래에 적어 두었음                                                |

- 실패율 임계값을 100이 아니라 50으로 둔 이유
  - 100으로 두면 절반쯤 살아있는 공급사를 끊지 않지만 거의 다 죽은 공급사도 끊지 않음
  - 청크 대부분이 실패하는 동안 결과 몇 건을 얻자고 검색 상한까지 쓰게 됨
  - 50이면 처음 나간 10개 중 절반이 실패할 때 끊음
  - 잃는 것은 처음 나간 호출들이 우연히 나빴을 때 나머지를 포기한다는 점임

#### 반열림 정원을 1로 둠
- 프로브는 공급사가 살아났는지 확인하는 것이 목적이므로 실제 작업을 여러 건 보낼 이유가 없음
- 인스턴스가 여러 대면 그 배수가 되므로 작을수록 나음
- 그래서 1로 둠
- `waitDurationInOpenState`는 공급사 복구 시간을 모르므로 도출할 수 없어 30초로 가정함
- 대기 시간이 지나면 호출 없이도 반열림으로 넘어가도록 `automaticTransitionFromOpenToHalfOpenEnabled`를 켜 둠
  - 끄면 다음 호출이 들어올 때까지 열린 상태로 남음
  - 검색이 뜸한 시간대에 공급사가 복구되어도 다음 검색이 올 때까지 그 사실을 모르게 되므로 켜는 쪽을 택함
#### 상태 표현
- 서킷이 열린 상태에서 던져지는 `CallNotPermittedException`은 sealed 클래스로 정한 예외의 종류 밖임
  - 그대로 두면 `onErrorResume`이 잡지 못해 검색 전체가 마비될 수 있음
  - `SupplierCircuitOpenException`으로 변환해 계열 안에 들임
- 공급사 상태에 `CIRCUIT_OPEN`을 추가함
  - 별도 상태로 둔 이유는 재시도 판단이 다르기 때문임
  - 다른 상태들은 재시도가 의미 있거나 없거나인데 이것만은 재시도하면 안 됨

#### 검토했지만 적용하지 않은 것
- 회복 판정을 검색 경로 밖으로 빼고 숙소 목록 API를 헬스체크로 쓰는 방법
  - 공급사가 헬스체크 엔드포인트를 준다면 주기적으로 확인해 서킷을 닫는 것이 맞음
  - 그러나 두 엔드포인트는 서로 다른 내부 시스템에 의존할 수 있음
  - 숙소 목록만 보고 회복을 판정하면 재고 조회가 여전히 죽어 있을 때 서킷이 닫혔다 열렸다를 반복함

### 재시도 정책
- 구현하지 않았으며 만약 도입한다면 아래를 따름

| 상태 | 재시도 | 이유 |
|---|---|---|
| `TIMEOUT` | 대상 | 일시적일 수 있음 |
| `SUPPLIER_ERROR` | 대상 | 공급사 측 서버 오류이며 회복될 수 있음 |
| `REQUEST_REJECTED` | 제외 | 같은 요청을 다시 보내도 같은 결과임 |
| `MALFORMED_RESPONSE` | 제외 | 응답 형식 문제라 재시도로 바뀌지 않음 |
| `CIRCUIT_OPEN` | 제외 | 서킷이 닫힐 때까지 기다려야 함 |

- 도입 시점에 함께 정해야 하는 것
  - 재시도 총량, 간격, 횟수임
  - 여기서 총량 제어가 가장 중요한데, 한 번에 많은 재시도가 공급사측에 몰리면 안되기 때문임
- 도입하지 않은 이유
  - 재시도 때문에 고객의 응답시간을 늦출 수 없음
  - 재시도가 필요한 상황이라면 이미 비정상적인 상황이라고 생각하기 때문에 써킷브레이커로 해당 공급사를 차단하는 게 맞다고 판단함

### 공급사 호출 한도

#### 레이트 리미터는 도입하지 않음
- 스펙에 429와 E429가 있으므로 공급사는 호출 한도를 가짐. 다만 값은 주어지지 않았음
- 어느 정도의 요청에 429 에러가 발생하는지 알 수 없기 때문에 이를 가정하기도 어렵다고 판단함
- 다만 실제 값이 존재한다면 레이트리미터를 둘 것임
