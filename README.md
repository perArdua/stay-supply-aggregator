# stay-supply-aggregator

외부 API에서 데이터를 받아 가공을 한 후 검색 결과를 제공하는 서버
고객, 공급사와의 3자 관계를 고려하여 설계함

---

## 빌드와 실행

### 준비

- Java 21
- Docker (MySQL 8.4)

### 1. DB 기동

```
docker compose up -d
```

`compose.yaml`이 MySQL 8.4를 13306 포트로 띄움. 스키마는 앱 기동 시 Flyway가 만듦.

### 2. Mock 공급사 두 개 기동

같은 애플리케이션을 `mock` 프로필로 포트만 바꿔 두 번 띄움. A는 9090, B는 9091임.

```
# 터미널 1 — Mock A
./gradlew bootRun --args='--spring.profiles.active=mock'

# 터미널 2 — Mock B
./gradlew bootRun --args='--spring.profiles.active=mock --server.port=9091'
```

`mock` 프로필은 DataSource 자동설정과 Flyway를 끄고, 동기화·검색 관련 빈을 만들지 않음.

### 3. 애플리케이션 기동

```
# 터미널 3
./gradlew bootRun
```

8080으로 뜸. 기동 시 매핑 테이블이 비어 있으면 공급사 숙소 목록을 한 번 동기화함.

### 5. 장애 상황 재현

Mock의 모드를 바꾸면 공급사가 고장난 상황을 만들 수 있음. A는 9090에, B는 9091에 보냄.

| 모드 | A | B |
|---|---|---|
| `normal` | 정상 응답 | 정상 응답 |
| `error` | HTTP 503 | HTTP 200 + `resultCode: E503` |
| `no-response` | 30초 무응답 | 30초 무응답 |
| `delay` | 5초 뒤 정상 응답 | 5초 뒤 정상 응답 |
| `empty` | 숙소 목록을 빈 배열로 반환 | (없음) |

**부분 실패 — A만 고장**

```
curl -X POST 'http://localhost:9090/control/a/mode?value=error'
curl "http://localhost:8080/api/v1/stays/search?checkIn=2026-09-01&checkOut=2026-09-04&adults=2&children=0"
```

B의 결과만 담아 200으로 응답함. A가 실패했다는 사실은 `suppliers`에 남음.

```json
{
  "offers": [ {"...": "B의 상품 1건"} ],
  "suppliers": [
    {"supplier":"A","status":"SUPPLIER_ERROR",
     "message":"1 of 1 chunks failed (SUPPLIER_ERROR): availability API responded 503 SERVICE_UNAVAILABLE"},
    {"supplier":"B","status":"OK","message":null}
  ]
}
```

**전체 실패 — 둘 다 고장**

```
curl -X POST 'http://localhost:9091/control/b/mode?value=error'
```

내보낼 상품이 하나도 없으므로 503으로 응답함.

```json
{
  "code": "ALL_SUPPLIERS_FAILED",
  "message": "every supplier failed; see suppliers for details",
  "suppliers": [
    {"supplier":"A","status":"SUPPLIER_ERROR","message":"..."},
    {"supplier":"B","status":"SUPPLIER_ERROR","message":"..."}
  ]
}
```

**되돌리기**

```
curl -X POST 'http://localhost:9090/control/a/mode?value=normal'
curl -X POST 'http://localhost:9091/control/b/mode?value=normal'
```

## 통합 모델 — 무엇을 표준으로 삼고 무엇을 버렸는가

두 공급사가 주는 정보가 겹치지 않기 때문에 겹치지 않는 부분은 둘 다 줄 수 있는 것으로 잡음.

### 요금은 기간 전체 총액, 세금 포함

- A는 날짜별 세금 별도 단가를 주고 B는 기간 전체 세금 포함 총액을 주므로 하나로 통일해야 함
- 숙박하는 날에 따라서 단가가 달라진다는 점을 생각해보았을 때 B가 주는 기간 전체 가격이 1박 가격들의 합이 아닐 가능성이 높다고 생각함
- 따라서 총액을 표준으로 삼음
  - A의 총액은 이 서비스가 각 날짜의 `nightlyRate`와 `taxAmount`를 더해 합산한 값임
  - B의 총액은 `totalPrice`를 그대로 씀
- 사용하는 사람 입장에서도 생각해보았는데, 어떤 기간동안 어디에 머물지를 결정할 때 1박 가격들을 확인하고 예약을 하는 것이 아니라 최종 결제할 금액을 기준으로 생각한다고 판단함

**얻는 것**

- 두 공급사의 상품을 같은 기준으로 비교할 수 있음
- 어느 공급사에서 왔는지와 무관하게 응답 형태가 같음

**잃는 것**

- 세금 표현이 공급사마다 달라짐. A는 세액을 알 수 있고 B는 알 수 없어 `taxAmount`가 한쪽만 채워짐
  - 세액이 얼마인지 표시해야 하는 요구사항이 생기면 수정이 필요함
- 부분 취소나 일부 날짜 변경이 생기면 합리적인 환불액을 산정할 근거가 없음
  - A는 날짜별 값을 갖고 있었으나 버렸고 B는 애초에 없음

**생각해봤지만 반영하지 않은 것**

- 날짜별 단가를 표준으로 삼고 B의 총액을 박수로 나눔
  - 공급사가 주지 않은 값을 만들어내기 때문에 고객에게 보여주는 숫자가 사실이 아님
- 두 형태를 모두 표준에 담고 공급사에 따라 한쪽만 채움
  - 공급사 간 차이가 응답 표면에 그대로 드러남
  - 클라이언트가 어느 필드를 볼지 공급사별로 분기해야 하므로 이 코드의 책임을 다른 개발자에게 넘기는 행위가 됨

**필드 구성**

| 필드 | 의미 | A | B |
|---|---|---|---|
| `totalAmountIncludingTax` | 기간 전체 고객 결제 금액 | 날짜별 합산 | `totalPrice` |
| `taxAmount` | 그중 세금 | 날짜별 `taxAmount` 합산 | `null` |
| `currency` | 통화 | 응답 그대로 | 응답 그대로 |
| `breakfastIncluded` | 요금에 조식이 포함되는지 | 응답 그대로 | 응답 그대로 |

- 이름에 `IncludingTax`를 넣은 이유
  - `totalAmount`만으로는 세금 포함 여부가 드러나지 않기 때문에 명확히 하기 위해 넣음
  - net과 gross는 공급사 스펙의 용어이므로 자사 모델에 쓰지 않음
- `taxAmount`를 B에서 `null`로 두는 이유
  - B는 `totalPrice`에 세금이 포함되어 있다는 것만 알려주고 세액은 주지 않음
  - 만약 null이 아닌 0으로 값을 놓는다면, 세금이 없는 상품과 구분되지 않음
- `breakfastIncluded`를 함께 노출하는 이유
  - 예시 데이터에서 같은 객실을 A는 조식 없이 429,000원에, B는 조식을 포함해 452,000원에 팜
  - 이 필드가 없으면 고객이 금액만 보고 조건이 다른 상품을 비교하게 됨
  - 요금을 비교 가능한 형태로 내놓는 것이 통합의 목적이므로 조건을 함께 노출함

**합산 대상은 요청 기간의 날짜로 한정함**

- 이 서비스는 A의 응답에서 요청 기간(checkIn 이상 checkOut 미만)에 해당하는 날짜만 골라 더함
- A가 기간 밖 날짜를 얹어 보내도 총액에 넣지 않음
  - 예약 가능 객실 수는 요청 기간만 보는데 요금이 응답 전체를 더하면, 같은 상품의 재고와 금액이 서로 다른 기간을 가리키게 됨

**요청 기간의 날짜가 빠져 있으면 총액과 세액을 함께 `null`로 내보냄**

- 고객이 4박을 요청했는데 A가 사흘치 요금만 주는 경우임
- 그대로 합산하면 3박 금액이 4박 상품의 가격으로 고객에게 보임
- 재고는 이 서비스가 모르는 날을 0으로 보아 틀려도 안전한 쪽으로 틀리지만, 금액에는 그런 방향이 없어 그냥 틀린 값이 됨
- 총액을 믿을 수 없는데 세액만 내보내는 것은 앞뒤가 맞지 않아 둘을 함께 비움. B의 `taxAmount`를 0이 아니라 `null`로 둔 것과 같은 규칙임
- 같은 상황에서 공급사 B의 상품은 `totalPrice`가 그대로 나감
  - A는 날짜마다 요금이 붙어 오므로 요청한 박수와 받은 날짜 수를 비교해 누락을 알 수 있음
  - B의 요금은 `totalPrice` 하나뿐이고 날짜가 붙어 있지 않음. 그 금액이 며칠치인지 B가 알려주지 않으므로 이 서비스가 누락을 판정할 근거가 없음
  - B도 재고에는 날짜가 오므로 `availableRooms`는 0이 됨. 다만 재고 행이 빠진 것이 요금도 그만큼 모자라다는 뜻인지는 알 수 없음
  - B가 금액에 기간을 붙여 주지 않는 한 판정할 수 없으므로 지금은 그대로 둠

### 예약 가능 객실 수는 기간 중 최솟값

- 예약 가능 객실 수의 정의가 요청 기간 전체를 예약할 수 있는 객실 수임
- 3박 중 하루라도 재고가 0이면 그 기간 전체를 예약할 수 없음
- 따라서 기간 내 날짜별 `remainingRooms`의 최솟값을 취함

```
A-10023  재고 3, 1, 5  →  최솟값 1
A-10044  재고 2, 0, 4  →  최솟값 0
```

**날짜가 일부 누락된 응답은 0으로 봄**

- 3박을 요청했는데 응답에 2일치만 오는 경우가 있을 수 있음
- 누락된 날의 재고를 모르는 상태이며, 이를 있다고 가정하면 예약할 수 없는 상품을 판매 가능으로 노출하게 됨
- 그래서 그 상품은 예약 불가 상태로 놓는 것이 맞다고 생각함
- 고객은 누락되었다는 사실을 알게 되면 서비스를 이용할 의욕이 저하되므로 누락 사실은 개발자만 알도록 남기는 것이 맞다고 생각함
- 검토했지만 적용하지 않는 부분
  - 응답에 없는 날짜를 무시하고 응답으로 온 날짜끼리만 최솟값을 구하는 방법
    - 3박을 요청했는데 2일치만 오면, 그 2일치만 보고 예약 가능하다고 판단하게 됨
    - 빠진 하루에 방이 없어서 예약이 실패해도 검색 결과에는 예약 가능으로 나옴
  - 스펙 위반으로 보고 예외를 던지면 하나의 이상 현상이 그 공급사 결과 전체를 날림

### 예약 불가 상품도 응답에 포함함

- `availableRooms`를 0으로 두어 그대로 노출함
- 고객이 그 숙소의 존재를 알고 날짜를 바꿔 다시 검색할 수 있음
- 응답에서 빼면 없는 숙소와 그 날짜에 방이 없는 숙소가 구분되지 않음
- 다만, 단점으로는 응답 크기가 커지고 클라이언트가 0을 걸러내는 처리를 해야 한다는 점이 있음
  - 응답 크기가 커지는 문제는 키워드, 페이징 등을 사용하면 해결 가능하지만 이 문서에서 다루는 범위 밖임
- 예약 가능 여부를 나타내는 별도 boolean 필드는 두지 않음
  - `availableRooms`가 0인 것이 곧 예약 불가이므로 같은 사실을 두 필드로 표현하게 됨

### 같은 숙소를 파는 두 공급사의 상품을 하나로 합치지 않음

A의 `A-10023`과 B의 `B77120`이 실제로는 같은 숙소지만, 각각 다른 내부 식별자를 부여하고 따로 노출함.

**공급사가 많아지면 합칠 필요가 있음**

- 이를테면 유명 호텔 하나를 공급사 수십 곳이 제공하게 되면 그 숙소가 목록을 채우게 됨
- 고객은 같은 호텔을 넘기기 위해 페이지를 넘기거나 스크롤 다운을 해야 함
- 즉 이 경우 검색 기능이 제대로 동작하지 않는 상황이라고 봐도 됨

**그럼에도 불구하고 지금 합치지 않는 이유**

- 공급사들이 같은 숙소를 판다는 사실을 조건문으로 알아내기 어려움
- 이로 인해 사람이 직접 관여해야 하고 공급사에 변경이 생기면 검증이 필요함
- 또한 같은 숙소로 판정되어 이를 고객이 예약했는데, 실제로 잡힌 숙소가 다를 수도 있다는 위험이 있음
- 즉, 이러한 검증 시스템은 별도의 시스템이나 모듈이 필요하다고 생각됨

같은 이유로 조식 포함 여부도 그대로 둠. A는 미포함 429,000원, B는 포함 452,000원임. 조건이 다른 두 상품을 하나로 합치면 고객이 무엇을 비교하는지 알 수 없게 됨.

## MVC 위에서 WebClient만 사용

- WebClient도 처음 쓰는 상황에서 WebFlux를 알아볼 여유가 안된다고 판단했음
- 외부 API를 호출할 때 중요한 것은 실패했을 때 어떻게 처리할 것인가라고 생각함
  - 속도 같은 것은 외부 공급사에서 요청처리가 늦는 경우 대응할 수 없지만
  - 외부 공급사가 모종의 이유로 응답이 느리거나 응답을 거절하는 경우에 대응하는 로직은 이 서버에서 컨트롤 할 수 있어서임

## 신규 공급사를 추가하는 절차

OCP를 지키는 코드로 작성함

A를 만든 뒤 B를 추가하며 실제로 손댄 곳을 기록함.
| 종류 | 내용 |
|---|---|
| 신규 클래스 | `adapter/b/` 3개 (Properties, Config, Client) |
| 기존 파일 추가 | `Supplier` enum 상수 1개 |
| 설정 추가 | `application.yaml`의 `suppliers.b` 블록 |
| 기존 로직 수정 | 0개 |

각 클래스에서 설정해야 하는 아래와 같음

- `adapter/c/SupplierCProperties` — base-url, api-key, 타임아웃 값
- `adapter/c/SupplierCConfig` — WebClient와 커넥션 풀
  - `adapter/c/SupplierCClient` — 호출과 표준 모델 변환

`Supplier` enum이 늘어나는 것은 OCP 위반으로 보지 않음
- 여기에 상수 추가를 강제하는 것이 등록 누락을 막는 장치라고 생각하기 때문임

**확장 시 예상되는 변형**

- 인증이 헤더가 아닌 방식인 경우
  - 해당 공급사의 Config만 수정하면 됨
- 목록이 페이징으로 오는 경우
  - 해당 공급사의 Client가 합쳐서 반환하면 되며 인터페이스는 그대로임
- 기존 네 분류에 없는 실패 표현을 가져오는 경우
  - 예외 계층 수정이 필요함

### 공통 코드를 만들지 않음

- A와 B의 Config와 Client는 코드가 거의 유사함
- 중복 코드가 발생한 것처럼 보임. 그럼에도 불구하고 추출하지 않기로 함

**추출하지 않은 이유**

1. 공급사마다 타임아웃에 대한 정책이 상이할 가능성이 있음
   - 공급사 서버마다 정책이 다른 경우 타임아웃 조건이 상이하여, 만약 공통 코드로 추출할 경우 각 타임아웃 설정 값이 특정 공급사의 timeout의 최소·최대 값으로 고정되어 유동적이지 못함
2. 공통 부모의 수정이 기존 공급사로 파급됨
   - 만약 신규 공급사가 기존 코드와 다른 요구사항을 충족해야 한다면 이미 만든 공급사 코드가 영향을 받음

| | 내용 |
|---|---|
| 얻는 것 | 한 공급사의 변경이 다른 공급사 파일을 건드리지 않음 |
| 잃는 것 | 비슷한 코드가 공급사 수만큼 반복됨. 공통 개선 시 모든 곳을 고쳐야 함 |

공급사별 요청·응답 형식은 어댑터 안에 갇혀 있고, 도메인 계층은 표준 모델만 봄.

## 숙소가 수천 개일 때

값 셋을 정했고 그 결과로 한 번의 검색이 다룰 수 있는 숙소 수가 정해짐.

| 값 | 정한 값 | 어떻게 정했는가 |
|---|---|---|
| 검색 상한 | 2000ms | 가정 |
| 동시 호출 상한 | 10 | 가정 |
| 호출 상한 | 500ms | 앞의 둘에서 계산한 뒤 조정 |
| 다룰 수 있는 숙소 수 | 1500개 | 위 셋에서 따라 나온 결과 |

- 보유 숙소가 그보다 많으면 뒤쪽 청크가 검색 상한에 잘려 결과가 덜 완전해짐

**정하는 순서**

1. 우리 쪽 고정 비용을 측정함. 예산에서 이 값을 먼저 빼야 하기 때문임
2. 검색 상한을 정함. 이 시스템에서 도출되지 않아 가정으로 둠
3. 동시 호출 상한을 정함. 이것도 도출되지 않아 가정으로 둠
4. 앞의 값들에서 호출 상한을 계산하고, 계산값이 공급사에게 지나치게 짧다고 보아 조정함
5. 조정한 결과로 다룰 수 있는 숙소 수가 정해짐

**다룰 수 있는 숙소 수는 검색 상한, 동시 호출 상한, 호출 상한에 따라 달라짐**

- 검색 하나가 만드는 공급사 호출이 여러 개임
  - 재고 조회 API가 한 번에 숙소 코드를 50개까지 받으므로 보유 숙소를 50개씩 청크로 나눔
  - 숙소가 4000개면 공급사당 청크가 80개가 됨
- 청크를 한꺼번에 다 보내지 않고 동시 호출 상한만큼만 보냄
  - 상한이 10이면 진행 중인 호출이 항상 10개 이하로 유지됨
  - 청크 80개를 10개씩 처리하면 8번에 나누어 보내게 됨
- 한 번 보낼 때 걸리는 시간은 길어야 호출 상한만큼임
- 따라서 최악의 경우 공급사 호출에 드는 시간은 나누어 보내는 횟수에 호출 상한을 곱한 값임
- 여기에 우리 쪽 고정 비용을 더한 것이 검색 전체에 걸리는 시간이고, 그것이 검색 상한 안에 들어와야 함
- 정리하면 검색 상한에서 고정 비용을 빼고 호출 상한으로 나누면 몇 번까지 나누어 보낼 수 있는지가 나오며, 거기에 동시 호출 상한과 청크당 숙소 수를 곱하면 다룰 수 있는 숙소 수가 나옴

**청크는 순차적으로 실행되는 것이 아님**

- `flatMapSequential`의 동시 호출 상한은 진행 중인 호출 개수의 상한임
  - 호출 하나가 끝나면 그 자리에 즉시 다음 청크가 들어감
  - 청크 10개가 모두 끝나기를 기다렸다가 다음 10개를 보내는 것이 아님
- 다만 정하려는 것이 최악의 경우 상한이므로 청크 10개가 모두 끝나기를 기다렸다가 다음 10개를 보내는 것이라고 가정함

**우리 쪽 고정 비용은 측정할 수 있음**

- 공급사 호출을 뺀 구간을 30회 측정했고 기준 지표는 p95임

| 구간 | 숙소 3개 | 숙소 4000개 |
|---|---|---|
| 컨트롤러 진입부터 매핑 조회 완료 | 2.7ms | 20.4ms |
| 마지막 청크 도착부터 응답 완료 | 1.3ms | 2.5ms |
| 합 | 4.0ms | 22.9ms |

- 매핑 조회가 숙소 수에 비례해 늘어남
  - 이 구간은 동기 JDBC라 요청 스레드가 묶임
  - 지금 규모에서는 병목이 아니지만 숙소 수가 더 늘어나면 튜닝이 필요할 수 있음
- 계산에서는 23ms로 잡음

**검색 상한은 최악의 경우 상한이며 평균이 아님**

- 정상 경로에서는 발동하지 않음
- 최악의 경우에 고객을 얼마나 붙잡아 둘 것인가임
- 장애 상황에서 고객은 최대 2초까지 기다릴 수 있다고 판단함
- 시간이 길어지면 고객은 서비스에서 이탈하고 다른 일을 하러 갈 수도 있음

**동시 호출 상한은 10으로 가정함**

- 한 공급사에 동시에 진행 중인 호출 수의 상한임
- 만약 상한이 없다면 공급사가 보유한 숙소 수에 비례하여 호출이 만들어짐
  - 숙소가 4000개 있다고 했을 때, 청크가 80개이므로 한 번에 80개의 요청이 만들어지는 것임
  - 공급사가 2개면 160개임
- 진행 중인 호출 하나가 커넥션 하나를 점유함
- 커넥션 풀이 감당하지 못할 정도로 요청이 많이 생성되면 요청은 대기하게 되는데, 이 대기 시간이 호출 상한에 포함되는 문제가 있음
  - 이 경우 공급사는 멀쩡한데 TIMEOUT으로 기록되어 실패 원인을 잘못 기록하게 됨
  - 이 우려는 테스트에서 실제로 발생함. 다만 대기가 아니라 대기 큐까지 꽉 차 호출이 거부되는 형태였고, 그때는 TIMEOUT이 아니라 공급사 서버 오류로 기록되고 있었음
  - 풀 포화를 `POOL_EXHAUSTED`로 따로 분류하고 서킷의 실패 집계에서 제외함. 다만 대기하다 호출 상한을 다 쓴 경우는 예외만으로 구분할 수 없어 여전히 TIMEOUT으로 남음
- 공급사 관점에서도 한 번에 많은 요청이 몰리는 것은 부담될 것임
- 다만 현 상황에서는 공급사의 호출 한도를 모르고 커넥션 풀도 Mock 환경에서는 제약이 되지 않기 때문에 임의로 10으로 정함
  - 이 값은 공급사별로 상한을 둔 것이므로 전역 상한은 공급사 수와 이 값을 곱한 값이 됨

**호출 상한은 계산한 뒤 조정함**

- 검색 상한 2000ms에서 고정 비용 23ms를 빼면 공급사 호출에 쓸 수 있는 시간이 1977ms임
- 숙소 4000개를 다루려면 청크 80개를 10개씩 8번에 나누어 보내야 하므로, 한 번에 허용되는 시간은 1977을 8로 나눈 247ms임
- 247ms를 그대로 쓰지 않았음
  - 측정할 때마다 어느 정도 달라지기 때문임
  - 공급사의 실제 응답 시간을 모르는 상태에서 247ms는 지나치게 짧다고 생각함
  - 이보다 느린 공급사의 정상 응답을 타임아웃으로 처리하게 됨
- 그래서 여유 있게 500ms로 올림
  - 그 대신 다룰 수 있는 숙소 수가 4000개에서 1500개로 줄어듦

**검색 상한을 줄이면 보낼 수 있는 숙소 수가 줄어듦**

| 검색 상한 | 나누어 보내는 횟수 | 숙소 |
|---|---|---|
| 5000ms | 9 | 4500개 |
| 3000ms | 5 | 2500개 |
| 2000ms | 3 | 1500개 |
| 1000ms | 1 | 500개 |

## 연동 견고성

외부 연동은 실패하므로 실패를 전제로 설계해야 함. 실패를 감지하고 끊는 지점이 층마다 다름.

| 층 | 장치 | 무엇을 막는가 |
|---|---|---|
| 호출 하나 | 호출 상한 | 응답이 오지 않는 호출이 무한정 기다리는 것 |
| 검색 요청 하나 | 검색 상한 | 청크 수에 비례해 응답 시간이 늘어나는 것 |
| 요청과 요청 사이 | 서킷 브레이커 | 죽은 공급사에 계속 호출을 보내는 것 |
| 응답 | 부분 실패 허용 | 한 공급사의 실패가 전체 실패가 되는 것 |
| 인스턴스 전체 | 커넥션 풀 | 공급사로 나가는 동시 요청이 무한정 늘어나는 것 |

설정한 값은 이렇음.

| 항목 | 값 | 근거 |
|---|---|---|
| 연결 상한 | 1000ms | TCP 연결 수립까지 |
| 숙소 목록 조회 상한 | 10000ms | 하루 한 번 배치라 고객이 기다리지 않음 |
| 재고 조회 상한 | 500ms | 검색 상한에서 역산 |
| 검색 상한 | 2000ms | 최악의 경우 고객이 기다릴 수 있는 시간으로 가정 |
| 공급사당 동시 호출 상한 | 10 | 공급사의 호출 한도를 모르므로 정한 값 |
| 공급사당 커넥션 풀 | 100 | 동시 호출 상한 10 × 동시 검색 10건 가정 |

### 타임아웃은 엔드포인트마다 다른 값을 둠

- 공급사는 하나지만 숙소 목록 조회와 재고 요금 조회의 성격이 다름

| | 숙소 목록 | 재고 요금 조회 |
|---|---|---|
| 호출 시점 | 하루 한 번 배치 | 고객 검색마다 |
| 응답 크기 | 보유 숙소 전체 | 숙소 50개 |
| 느릴 때 생기는 일 | 동기화가 늦어짐 | 고객이 기다림 |

- 두 API가 서로 다른 내부 시스템에 의존할 수도 있음
  - 숙소 목록 API는 정상이지만 재고 요금 조회 API가 비정상인 상황이 있을 수 있음
- 따라서 타임아웃과 서킷을 거는 단위는 공급사가 아니라 공급사의 엔드포인트임

```yaml
property-list-timeout-millis: 10000
availability-timeout-millis: 500
```

- 같은 공급사가 무응답일 때 검색은 0.53초, 동기화는 10.03초에 끊김
- 다만 검색 쪽 값은 청크가 1개인 규모 기준이며, 숙소가 늘면 서킷과 검색 상한이 함께 관여함

### 검색 상한

**두는 이유**

- 완료 조건을 모든 호출이 끝나는 시점으로 두면 응답 시간이 가장 느린 호출에 좌지우지됨
- 상한을 두면 청크 수와 무관하게 응답 시간이 고정됨

**잘린 청크는 TIMEOUT으로 집계함**

- 검색 상한에 걸려 도착하지 못한 청크는 응답에서 `TIMEOUT`으로 나감
  - 청크의 결과를 받지 못했기 때문임

| | 내용 |
|---|---|
| 얻는 것 | 청크 수와 무관하게 응답 시간의 상한이 고정됨 |
| 잃는 것 | 커버 범위를 넘는 규모에서는 뒤쪽 청크가 잘려 결과가 덜 완전해짐 |

- 응답이 느린 것보다 결과가 덜 완전한 쪽이 낫다고 판단함. 고객에게 빨리 응답해야 하기 때문임

### 실패 판정을 통일함

B는 장애 상황에서도 HTTP 200을 주고 본문 `resultCode`로만 실패를 알림. 어댑터가 이것을 A의 5xx와 같은 실패로 바꿈. 공급사별 실패 표현이 도메인 계층으로 새어 나가지 않음. 자세한 분류는 `docs/adapter-design.md`의 「실패 판정 통일」 절에 있음.

### 부분 실패를 허용함

한 공급사가 응답하지 않아도 나머지 결과로 응답함. 실패한 공급사는 응답의 `suppliers`에 상태와 함께 남음.

### 커넥션 풀

**공급사별로 나눔**

- 공유하면 A가 커넥션을 붙잡고 있을 때 B의 획득까지 밀림
  - 타임아웃도 서킷도 공급사 단위로 갈라 놨는데 커넥션만 공유하면 격리가 마지막 단계에서 깨짐
- "공급사당 동시 호출 10"이라는 상한도 공유 풀에서는 A가 다 쓰면 B 몫이 없어져 뜻을 잃음
- 잃는 것은 한쪽 풀이 남아도 다른 쪽이 못 쓴다는 점인데, 격리가 더 중요하다고 판단함

**크기**

- 검색 한 건이 한 공급사에 쓰는 커넥션은 최대 10개임. 동시 호출 상한과 같음
- 동시 검색 N건이면 10N임
- 동시 검색 수는 10이라고 가정했음
- 따라서 공급사당 100으로 설정

```yaml
max-connections: 100
```

### 서킷 브레이커

**도입한 이유**

- 서킷이 없으면 공급사 A가 죽어 있어도 검색할 때마다 청크를 계속 보냄
- 두 가지를 막기 위해 도입
  - 고객이 죽은 공급사를 기다리는 시간
  - 죽은 공급사로 나가는 무의미한 호출

**검색 상한과 역할이 다름**

| | 검색 상한 | 서킷 |
|---|---|---|
| 보는 것 | 검색 시작 후 흐른 시간 | 청크 호출의 실패 비율 |
| 상태가 남는 범위 | 요청 안 | 요청 사이 |

- 공급사가 완전히 죽으면 서킷에 의해 검색 상한은 발동하지 않음
- 검색 상한이 필요한 상황은 서킷이 열리지 않는 경우임
  - 실패율이 임계값 아래로 유지되면서 응답만 계속 느린 상태

**청크 단위에 걺**

- 실패를 세는 단위가 청크여야 80개 중 몇 개 실패라는 값이 의미를 가짐
- 공급사 단위로 걸면 한 번의 성공 또는 실패로만 집계되어 임계값이 뜻을 잃음
- 서킷 인스턴스 이름을 `A-availability` 형태로 둠

**애노테이션이 아니라 연산자를 씀**

- `@CircuitBreaker`와 fallback 방식을 검토했으나 두 가지가 걸림
  - fallback이 실행되면 예외가 상위로 전파되지 않음. 즉 예외 종류를 분기하는 switch까지 도달하지 못하므로, 경우를 빠짐없이 다뤘는지 컴파일러가 검사해 주던 것이 무의미해짐
  - 서킷이 어디에 걸렸는지 코드에 드러나지 않음
- `CircuitBreakerOperator`를 `transformDeferred`로 거는 방식은 예외가 그대로 올라와 기존 처리 경로를 탐

**설정값과 근거**

| 값 | 근거 |
|---|---|
| `slidingWindowType: COUNT_BASED` | 호출 개수로 셈 |
| `slidingWindowSize: 10` | 동시 호출 상한과 동일 |
| `minimumNumberOfCalls: 10` | 이보다 작으면 처음 나간 호출들의 결과가 도착하기 전에 판정하게 됨 |
| `failureRateThreshold: 50` | 결과를 덜 받더라도 빨리 끝내는 쪽 |
| `permittedNumberOfCallsInHalfOpenState: 1` | 아래에 적어 두었음 |
| `waitDurationInOpenState: 30s` | 도출된 값이 아님 |
| `automaticTransitionFromOpenToHalfOpenEnabled: true` | 아래에 적어 두었음 |
| `ignoreExceptions` | 커넥션 풀 포화는 우리 쪽 문제라 공급사의 실패율에 넣지 않음 |

- 실패율 임계값을 100이 아니라 50으로 둔 이유
  - 100으로 두면 절반쯤 살아있는 공급사를 끊지 않지만 거의 다 죽은 공급사도 끊지 않음
  - 청크 대부분이 실패하는 동안 결과 몇 건을 얻자고 검색 상한까지 쓰게 됨
  - 50이면 처음 나간 10개 중 절반이 실패할 때 끊음
  - 잃는 것은 처음 나간 호출들이 우연히 나빴을 때 나머지를 포기한다는 점임

**반열림 정원을 1로 둠**

- 프로브는 공급사가 살아났는지 확인하는 것이 목적이므로 실제 작업을 여러 건 보낼 이유가 없음
- 인스턴스가 여러 대면 그 배수가 되므로 작을수록 나음
- `waitDurationInOpenState`는 공급사 복구 시간을 모르므로 도출할 수 없어 30초로 가정함
- 대기 시간이 지나면 호출 없이도 반열림으로 넘어가도록 `automaticTransitionFromOpenToHalfOpenEnabled`를 켜 둠
  - 끄면 다음 호출이 들어올 때까지 열린 상태로 남음
  - 검색이 뜸한 시간대에 공급사가 복구되어도 다음 검색이 올 때까지 그 사실을 모르게 되므로 켜는 쪽을 택함

**상태 표현**

- 서킷이 열린 상태에서 던져지는 `CallNotPermittedException`은 sealed 클래스로 정한 예외의 종류 밖임
  - 그대로 두면 `onErrorResume`이 잡지 못해 검색 전체가 마비될 수 있음
  - `SupplierCircuitOpenException`으로 변환해 계열 안에 들임
- 공급사 상태에 `CIRCUIT_OPEN`을 추가함
  - 별도 상태로 둔 이유는 재시도 판단이 다르기 때문임
  - 다른 상태들은 재시도가 의미 있거나 없거나인데 이것만은 재시도하면 안 됨

**검토했지만 적용하지 않은 것**

- 회복 판정을 검색 경로 밖으로 빼고 숙소 목록 API를 헬스체크로 쓰는 방법
  - 공급사가 헬스체크 엔드포인트를 준다면 주기적으로 확인해 서킷을 닫는 것이 맞음
  - 그러나 두 엔드포인트는 서로 다른 내부 시스템에 의존할 수 있음
  - 숙소 목록만 보고 회복을 판정하면 재고 조회가 여전히 죽어 있을 때 서킷이 닫혔다 열렸다를 반복함

## 구현한 것과 하지 않은 것

### 구현

- 공급사 코드 ↔ 내부 식별자 매핑 저장 (숙소·객실 타입 두 단계)
- 기동 시 1회 + 하루 한 번(04:00) + 수동(`POST /internal/sync`) 매핑 동기화
- 공급사 어댑터 두 벌
- 통합 검색 API. 청크 분할, 공급사별 병렬 호출, 정규화, 병합
- 타임아웃, 부분 실패 허용, 실패 판정 통일, 서킷 브레이커
- Mock 공급사 (정상 / 장애 / 무응답 / 지연 / 빈 목록)
- 테스트 94개. 연박 판정, 청크 상한, 요금 합산, 실패 분류, 설정 바인딩, 빈 조립, 요청부터 응답까지의 흐름을 다룸

### 설계만 하고 구현하지 않음

- **연동 지표와 모니터링** (`docs/observability.md`) — 무엇을 왜 재는지까지만 정함
- **재시도 정책** — 넣지 않음. 재시도가 의미를 가지지 못한다고 생각하고, 오히려 재시도를 넣음으로써 재시도 총량 제어 등 다른 기술들이 들어가야 하기 때문임
